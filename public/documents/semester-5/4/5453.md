# Lenguajes de Programación - Paradigma orientado a objetos

## 5.3 Modelado y representación de objetos.

---

Programar con objetos requiere dos decisiones de naturaleza distinta. La primera es de **modelado**: qué objetos hay en el dominio del problema, qué responsabilidades tiene cada uno y cómo se relacionan. La segunda es de **representación**: cómo guarda el lenguaje un objeto en memoria y cómo encuentra sus campos y métodos. Este tema trata ambas: la estructura de un objeto en memoria y su modelo matemático, las relaciones entre clases de UML, el modelado del comportamiento con estados, la serialización y las métricas de cohesión y acoplamiento.

### Representación en memoria

Un objeto tiene **identidad**, **estado** y **comportamiento**. En una implementación típica, como la de Java o C++, un objeto es un bloque de memoria con:

- una **cabecera**, con un apuntador a la descripción de su clase, que incluye la tabla de métodos del tema 5.4, y datos para el recolector de basura y la sincronización;
- los **campos**, en posiciones fijas que el compilador conoce, con los de la superclase primero, de modo que el código compilado para la superclase encuentra sus campos en el mismo desplazamiento dentro de un objeto de cualquier subclase.

Los métodos no se guardan en el objeto: se comparten en la clase. La identidad es la dirección, y por eso `==` en Java compara identidad y `equals` compara estado.

En Python y JavaScript, por omisión, los campos viven en un **diccionario** por objeto, lo que permite agregar atributos en tiempo de ejecución a costa de memoria y tiempo de búsqueda. Con `__slots__`, Python usa posiciones fijas, como Java. Los motores de JavaScript, como V8, recuperan esa eficiencia con **clases ocultas**: agrupan los objetos que tienen los mismos campos en el mismo orden y les asignan una disposición fija.

### Modelo matemático

En la codificación de Cook y de Pierce, una clase es una función que recibe el estado y `self` y devuelve un registro de métodos, y un objeto es el punto fijo de la clase aplicada a un estado particular:

$$\mathit{clase} : \mathit{Estado} \to (\mathit{Obj} \to \mathit{Obj}), \qquad o = \mathsf{fix}(\mathit{clase}(s)).$$

Un objeto es así un **registro de cerraduras** que comparten el estado $s.$ La herencia combina registros antes de tomar el punto fijo, lo que da la recursión abierta del tema 5.1. El cálculo de objetos de Abadi y Cardelli toma en cambio los objetos como primitivos, sin clases: un objeto es un registro de métodos con un parámetro `self` explícito, y la herencia se reemplaza por la clonación y la actualización de métodos, como en Self y JavaScript.

### Relaciones entre clases

UML distingue, de más débil a más fuerte:

- **Dependencia:** una clase usa otra temporalmente, por ejemplo como parámetro de un método.
- **Asociación:** los objetos de una clase conocen a los de otra de forma duradera, con una **multiplicidad**: un curso tiene un profesor, un profesor tiene varios cursos. Si la asociación tiene datos propios, como la calificación de un estudiante en un curso, se modela con una **clase de asociación**.
- **Agregación:** una asociación todo-parte en la que las partes existen por separado: un departamento agrupa profesores.
- **Composición:** una agregación en la que el todo **posee** las partes, que se crean y destruyen con él y no se comparten: los horarios de un curso, las líneas de una factura.
- **Generalización:** la herencia, entre una clase y su especialización.

En el código, una asociación es un campo que referencia a otro objeto, y la composición, un campo que guarda un objeto creado por el propio todo, a menudo un **objeto valor**, inmutable y sin identidad propia, que se compara por contenido.

### Modelado del comportamiento

Muchos objetos tienen un ciclo de vida: un producto está disponible, reservado o agotado, y solo ciertas operaciones son válidas en cada estado. Hay dos maneras de representarlo:

- un **campo de estado** que se actualiza en cada transición, con el riesgo de que deje de coincidir con los datos de los que debería depender;
- un estado **derivado**, calculado a partir de los datos cada vez que se consulta, que nunca se desincroniza.

Cuando el comportamiento cambia mucho de un estado a otro, el patrón **estado** representa cada estado como un objeto con los métodos válidos en él, y el objeto principal delega en su estado actual.

### Métricas

La **cohesión** mide qué tanto pertenecen juntos los elementos de una clase; el **acoplamiento**, cuánto depende una clase de otras. El objetivo es **alta cohesión** y **bajo acoplamiento**. La métrica LCOM, de Chidamber y Kemerer (1994), cuenta los pares de métodos que no comparten atributos, $P,$ y los que sí comparten alguno, $Q:$

$$\mathrm{LCOM} = \max(P - Q, 0).$$

Un valor de 0 indica una clase cohesiva; uno alto, una clase con varias responsabilidades que convendría separar. La métrica CBO, del mismo trabajo, cuenta las clases con las que una clase está acoplada. Son indicadores, no reglas: una clase de datos sin métodos que compartan nada puede tener un LCOM alto y estar bien diseñada.

def a_json(obj, _vistos=None):
    """Reflexión sobre los campos públicos; escapa cadenas y detecta ciclos."""
    vistos = _vistos if _vistos is not None else set()
    if obj is None or isinstance(obj, (bool, int, float)): return json.dumps(obj)
    if isinstance(obj, str): return json.dumps(obj, ensure_ascii=False)
    if isinstance(obj, Enum): return a_json(obj.value, vistos)
    if id(obj) in vistos: raise ValueError(f"ciclo en {type(obj).__name__}")

    if isinstance(obj, (list, tuple)): return "[" + ", ".join(a_json(x, vistos) for x in obj) + "]"

# ---------- Cohesión: falta de cohesión de métodos (LCOM) a partir del código ----------
def lcom(cls):
    """LCOM de Chidamber y Kemerer: pares de métodos sin atributos en común menos pares con alguno, mínimo 0."""
    usos = {}
    for nombre, f in vars(cls).items():
        if inspect.isfunction(f) and not nombre.startswith("__"):
            arbol = ast.parse(textwrap.dedent(inspect.getsource(f)))
            usos[nombre] = {n.attr for n in ast.walk(arbol) if isinstance(n, ast.Attribute) and isinstance(n.value, ast.Name) and n.value.id == "self"}
    ms = list(usos); P = Q = 0
    for i in range(len(ms)):
        for j in range(i + 1, len(ms)):
            if usos[ms[i]] & usos[ms[j]]: Q += 1
            else: P += 1
    return max(P - Q, 0), usos
class Mezcla:                                                          # dos responsabilidades en una clase
    def __init__(self): self.saldo = 0; self.log = []
    def deposita(self, n): self.saldo += n
    def retira(self, n): self.saldo -= n
    def escribe(self, s): self.log.append(s)
    def vacia(self): self.log.clear()
for c in (Inventario, Mezcla):
    v, usos = lcom(c); print(f"cohesión: LCOM({c.__name__}) = {v}", {m: sorted(a) for m, a in usos.items()})

### Soluciones

**Ejercicio 1.** El diagrama de la sección de relaciones es el modelo. `Estudiante` y `Profesor` heredan de `Persona`. `Curso` se **asocia** con un profesor, que existe por su cuenta, y está **compuesto** de sus horarios, objetos valor inmutables que solo existen como parte del curso. La relación entre estudiantes y cursos es de muchos a muchos y tiene un dato propio, la calificación, por lo que se modela con la **clase de asociación** `Matricula`, que ambos lados referencian. Las reglas del dominio están en un solo lugar, la función `matricula`: rechaza la inscripción si el curso no tiene cupo o si alguno de sus horarios se cruza con uno de los cursos ya inscritos; dos intervalos $[a, b)$ y $[c, d)$ del mismo día se cruzan si $a \lt d$ y $c \lt b.$ La calificación se valida en `Matricula.califica`. El promedio de Ana, con 9.5 y 8, es 8.75.

**Ejercicio 2.** La versión ingenua concatena cadenas, `"{\"nombre\": \"" + nombre + ...`, y produce JSON inválido en cuanto el nombre tiene una comilla, una diagonal invertida o un salto de línea; peor, si el nombre lo controla un usuario, puede **inyectar** campos. La solución es escapar cada cadena según la especificación de JSON, RFC 8259, o usar una biblioteca, como `json.dumps` en Python o Jackson en Java. El serializador del programa recorre por **reflexión** los campos públicos del objeto, omite los que empiezan con `_`, para no exponer datos internos, y trata recursivamente listas, diccionarios y objetos anidados. Detecta los **ciclos** con el conjunto de objetos en el camino actual: un objeto que se contiene a sí mismo no tiene representación en JSON. La prueba de corrección es la ida y vuelta: `json.loads` de la salida reproduce los datos. En Java, con la interfaz del enunciado, `toJSON` sería:

```java
public String toJSON() {
    return "{\"nombre\": " + escapa(nombre) + ", \"edad\": " + edad + "}";
}
static String escapa(String s) {
    StringBuilder sb = new StringBuilder("\"");
    for (char c : s.toCharArray()) {
        switch (c) {
            case '"' -> sb.append("\\\"");
            case '\\' -> sb.append("\\\\");
            case '\n' -> sb.append("\\n");
            default -> { if (c < 0x20) sb.append(String.format("\\u%04x", (int) c)); else sb.append(c); }
        }
    }
    return sb.append('"').toString();
}
```

**Ejercicio 3.** `Producto` guarda la existencia y lo reservado; `Perecedero` hereda y agrega la fecha de caducidad, y la categoría es un campo y no una subclase, porque no cambia el comportamiento. El `Inventario` está **compuesto** de sus productos y de un registro de movimientos. El estado **se deriva** del stock: agotado si la existencia es 0, reservado si todo lo existente está reservado, disponible en otro caso. Así es imposible que el estado diga "disponible" sin unidades libres. Las operaciones validan sus precondiciones: no se reserva más de lo libre ni se entrega más de lo reservado. La traza del teclado recorre los tres estados y muestra la reserva rechazada. El registro de movimientos permite reconstruir el inventario y auditarlo, y es el germen del patrón de **fuente de eventos**.

La métrica final confirma el diseño: `Inventario` tiene LCOM 0, porque todos sus métodos comparten `productos`, mientras que una clase que mezcla un saldo y una bitácora tiene LCOM 2, la señal de que son dos clases.
