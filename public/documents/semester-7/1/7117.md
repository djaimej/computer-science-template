# Compiladores - Introducción a lo que es un compilador

## 1.7 Resumen y perspectiva.

---

Este tema cierra la introducción: resume qué es un compilador y cómo se organiza, recorre brevemente su historia y presenta las direcciones en que evoluciona, con un recorrido real por GCC y Clang que muestra cada etapa de la compilación y lo que hacen los optimizadores actuales con programas sencillos.

### Resumen

Un compilador traduce un programa a otro lenguaje **preservando su significado** y, de ser posible, **mejorándolo**. Se organiza en un *front-end*, que entiende el programa y detecta sus errores con el análisis léxico, sintáctico y semántico; una o varias **representaciones intermedias**, sobre las que trabaja el optimizador, y un *back-end*, que selecciona las instrucciones, asigna los registros y ordena el código para una máquina concreta. Las estructuras que comparten son la tabla de símbolos, el árbol sintáctico, el código de tres direcciones y el grafo de flujo de control. Las fases de análisis se apoyan en la teoría de lenguajes formales y son lineales; las de síntesis enfrentan problemas NP-difíciles que se resuelven con heurísticas.

```mermaid
flowchart LR
    F["Fuente"] --> FE["Front-end: léxico, sintáctico, semántico"]
    FE --> IR["IR"]
    IR --> OP["Optimizador"]
    OP --> BE["Back-end: selección, registros, planificación"]
    BE --> O["Código objeto"]
```

### Una historia breve

| Época | Hitos |
| ----- | ----- |
| Años 50 | ensambladores; el sistema A-0 de Grace Hopper (1952); el primer compilador de **FORTRAN** (Backus y otros, 1957), que ya optimizaba para competir con el código escrito a mano |
| Años 60 | ALGOL 60 y la notación BNF; análisis sintáctico descendente; las gramáticas LR de Knuth (1965) |
| Años 70 | C y UNIX; los generadores Lex y Yacc; el análisis de flujo de datos de Allen y Cocke; la compilación de Pascal a P-código |
| Años 80 | arquitecturas RISC, que trasladan la complejidad al compilador; asignación de registros por coloreo de grafos (Chaitin, 1982); GCC (1987); la forma SSA (Cytron y otros, 1989-1991) |
| Años 90 | compiladores JIT para Java y Self; optimización entre procedimientos |
| Años 2000 | LLVM (2003); compilación para multinúcleos y vectorización automática; el modelo poliédrico; CompCert, un compilador de C verificado formalmente |
| Desde 2010 | Roslyn, el compilador de C# con interfaces para herramientas; compiladores para GPU y aprendizaje automático, como XLA y TVM; MLIR; WebAssembly; heurísticas aprendidas con aprendizaje automático, como MLGO en LLVM |

### Tendencias

- **Hardware heterogéneo:** el mismo programa debe ejecutarse en CPU, GPU y aceleradores; OpenMP y OpenACC agregan directivas para descargar ciclos, y MLIR permite definir representaciones intermedias por dominio que se van **bajando** de nivel.
- **Aprendizaje automático en el compilador:** modelos que deciden cuándo expandir una función en línea o cómo asignar registros, entrenados con muchos programas, y búsqueda automática de la mejor combinación de optimizaciones, el *autotuning*.
- **Seguridad y verificación:** compiladores verificados como CompCert, mitigaciones generadas por el compilador, como los *stack canaries* o la integridad del flujo de control, y lenguajes con garantías de memoria, como Rust, cuyo verificador de préstamos es parte del compilador.
- **Compilación incremental:** recompilar solo lo que cambió, como hacen el compilador de Rust y los servidores de lenguaje de los editores.
- **Computación cuántica:** compiladores que traducen algoritmos a circuitos y los adaptan a la conectividad y los errores de cada procesador cuántico, como Qiskit; Q# es un lenguaje para describir esos algoritmos.

### Implementación en Python

El programa hace con herramientas reales el recorrido de los tres primeros ejercicios: lleva el programa de la suma por el preprocesador y por gcc sin optimizar y con `-O2`, y lo ejecuta; obtiene la representación intermedia de LLVM de `factorial` con clang en tres niveles, y compila `calcular` con gcc en los niveles `-O0` a `-O3`, contando instrucciones y detectando instrucciones vectoriales.

```python
import os, re, subprocess, tempfile

D = tempfile.mkdtemp()
def corre(*cmd): return subprocess.run(cmd, capture_output=True, text=True, cwd=D, env={**os.environ, "LC_ALL": "C"})
def instrucciones(archivo):
    return [" ".join(l.split()) for l in open(os.path.join(D, archivo)) if l.startswith("\t") and not l.strip().startswith(".")]
OPC = ["-fno-asynchronous-unwind-tables", "-fcf-protection=none", "-masm=intel"]

# ---------- Ejercicio 1: el programa de la suma a través de gcc ----------
SUMA = '#include <stdio.h>\n\nint main() {\n    int suma = 0;\n    for (int i = 1; i <= 10; i++) {\n        suma += i;\n    }\n    printf("Suma: %d\\n", suma);\n    return 0;\n}\n'
open(os.path.join(D, "suma.c"), "w").write(SUMA)
pre = corre("gcc", "-E", "suma.c").stdout
print(f"ejercicio 1: preprocesado: {len(SUMA.splitlines())} líneas → {len(pre.splitlines())} líneas, con las declaraciones de stdio.h")
for nivel in ("-O0", "-O2"):
    corre("gcc", nivel, "-S", *OPC, "-o", f"suma{nivel}.s", "suma.c"); ins = instrucciones(f"suma{nivel}.s")
    saltos = [i for i in ins if re.match(r"j[a-z]+ ", i)]
    print(f"   gcc {nivel}: {len(ins)} instrucciones, {len(saltos)} saltos; carga el 55 como constante: {any('55' in i for i in ins)}")
print("   instrucciones con -O2:", " | ".join(instrucciones("suma-O2.s")))
corre("gcc", "-O2", "-o", "suma", "suma.c"); print("   ejecución:", corre("./suma").stdout.strip())

# ---------- Ejercicio 2: la representación intermedia de LLVM para factorial ----------
FACT = "int factorial(int n) {\n    if (n <= 1) return 1;\n    else return n * factorial(n - 1);\n}\n"
open(os.path.join(D, "fact.c"), "w").write(FACT)
for nivel in ("-O0", "-O1", "-O2"):
    corre("clang", nivel, "-S", "-emit-llvm", "-fno-discard-value-names", "-o", f"fact{nivel}.ll", "fact.c")
    ir = [l.rstrip() for l in open(os.path.join(D, f"fact{nivel}.ll"))]
    i = next(k for k, l in enumerate(ir) if l.startswith("define")); j = ir.index("}", i)
    cuerpo = [re.sub(r", !\w+ !\d+|, align \d+| #\d+", "", l) for l in ir[i:j + 1] if l.strip()]
    print(f"ejercicio 2: clang {nivel}: {len(cuerpo) - 2} líneas; llamadas a factorial: {sum('@factorial(' in l and 'call' in l for l in cuerpo)}; "
          f"operaciones vectoriales: {sum('<4 x i32>' in l for l in cuerpo)}")
    if nivel == "-O1":
        for l in cuerpo: print("   " + l)

# ---------- Ejercicio 3: la misma función en varios niveles ----------
CALC = "int calcular(int* array, int size) {\n    int total = 0;\n    for (int i = 0; i < size; i++) {\n        total += array[i] * 2;\n    }\n    return total;\n}\n"
open(os.path.join(D, "calc.c"), "w").write(CALC)
for nivel in ("-O0", "-O1", "-O2", "-O3"):
    corre("gcc", nivel, "-S", *OPC, "-o", f"calc{nivel}.s", "calc.c"); ins = instrucciones(f"calc{nivel}.s")
    vect = sorted({i.split()[0] for i in ins if re.match(r"(p(?!ush|op)[a-z]+|movdq[au]|vp[a-z]+) ", i)})
    mult = sorted({i.split()[0] for i in ins if re.match(r"(imul|add|lea|sal|psll[dq]|paddd) ", i)})
    print(f"ejercicio 3: gcc {nivel}: {len(ins):2} instrucciones; vectoriales {vect or 'ninguna'}; aritmética {mult}")
```

### Ejercicios Propuestos

1. **Análisis integral.** Traza el proceso completo de compilación del siguiente código:

    ```c
    #include <stdio.h>

    int main() {
        int suma = 0;
        for (int i = 1; i <= 10; i++) {
            suma += i;
        }
        printf("Suma: %d\n", suma);
        return 0;
    }
    ```

2. **Representación intermedia.** Propón una representación intermedia para:

    ```python
    def factorial(n):
        if n <= 1:
            return 1
        else:
            return n * factorial(n-1)
    ```

3. **Optimización en varios niveles.** Optimiza el siguiente código en diferentes niveles:

    ```c
    int calcular(int* array, int size) {
        int total = 0;
        for (int i = 0; i < size; i++) {
            total += array[i] * 2;
        }
        return total;
    }
    ```

4. **Tendencias.** Compara tres compiladores modernos, GCC, Clang y Roslyn, en su arquitectura modular, sus técnicas de optimización y su soporte de nuevos estándares.

5. **Diseño futuro.** Propón características para un compilador del año 2030, considerando el hardware heterogéneo, la programación asistida por IA y los requisitos de seguridad.

### Soluciones

**Ejercicio 1.** El **preprocesador** reemplaza `#include <stdio.h>` por el contenido del archivo, y las 10 líneas se vuelven más de 800, sobre todo declaraciones. El **análisis léxico** produce tokens como `int`, `<ID, main>`, `(`, `)`, `{`, `<ID, suma>`, `=`, `<NUM, 0>`; el **sintáctico**, un árbol con una declaración, un `for` con su inicialización, condición, incremento y cuerpo, y una llamada; el **semántico** registra `suma` e `i`, esta última en el ámbito del `for`, y verifica la llamada a `printf` contra su declaración. El **código intermedio** tiene un ciclo con su condición y su salto de regreso. Sin optimizar, gcc genera 20 instrucciones con 2 saltos que implementan el ciclo; con `-O2`, el optimizador propaga constantes, desenrolla el ciclo de 10 iteraciones y **calcula la suma al compilar**: el código final carga 55 en el registro del segundo argumento y llama a `printf`, sin ciclo. gcc además cambia `printf` por `__printf_chk`, una versión con verificaciones de seguridad que Ubuntu habilita por omisión. El **ensamblador** traduce a código de máquina y el **enlazador** une el objeto con la biblioteca de C; el programa imprime `Suma: 55`.

**Ejercicio 2.** Una buena IR es un **grafo de flujo de control** con bloques básicos en código de tres direcciones. Clang sin optimizar produce exactamente eso en LLVM IR, con un bloque para la comparación, uno por rama y una llamada recursiva. Con `-O1` hace algo notable: la **eliminación de la recursión de cola**, con un acumulador, convierte la función en un ciclo sin llamadas. La recursión original no es de cola, porque después de la llamada falta multiplicar, pero como la multiplicación es asociativa, LLVM introduce el acumulador y la transforma. El resultado está en **forma SSA**: cada variable se asigna una sola vez, y las instrucciones `phi` al inicio del bloque `tailrecurse` eligen el valor según de dónde llegó el control, 1 y `n` en la primera vuelta y los nuevos valores después. Con `-O2` además **vectoriza** el ciclo, multiplicando cuatro factores a la vez, con 12 operaciones vectoriales.

**Ejercicio 3.** Cada nivel agrega transformaciones:

- **en el código fuente:** como $\sum 2 a_i = 2 \sum a_i$ en aritmética entera modular, la multiplicación puede sacarse del ciclo y hacerse una vez al final;
- **`-O1`:** las variables pasan a registros y el ciclo se simplifica, de 22 a 15 instrucciones;
- **`-O2`:** el ciclo se reorganiza con un apuntador que avanza en lugar de un índice, y la multiplicación por 2 se hace con `add` o `lea`, más baratas que `imul`, 13 instrucciones;
- **`-O3`:** la **vectorización** procesa 4 enteros por instrucción con SSE: `movdqu` carga 4 elementos, `pslld` los multiplica por 2 desplazando un bit, `paddd` los acumula, y al final `psrldq` y `paddd` reducen los 4 acumuladores; el código crece a 50 instrucciones para manejar los elementos que sobran, pero cada vuelta procesa 4 elementos.

Más código no significa más lento: la versión de `-O3` es la más rápida para arreglos grandes.

**Ejercicio 4.** Una comparación resumida:

| | GCC | Clang con LLVM | Roslyn |
| - | --- | -------------- | ------ |
| Arquitectura | *front-ends* por lenguaje, IR GENERIC, GIMPLE en SSA y RTL; históricamente monolítico, con complementos | bibliotecas reutilizables; LLVM IR en SSA común a muchos lenguajes, como C, C++, Rust, Swift y Julia | compilador de C# y Visual Basic como servicio: árboles sintácticos y semánticos accesibles desde las herramientas y el IDE |
| Optimización | muy madura; optimización en tiempo de enlace, vectorización, poliédrica con Graphite | comparable; ThinLTO, vectorización, MLGO | genera IL; la optimización fuerte la hace el JIT RyuJIT o la compilación anticipada de .NET |
| Estándares | C23, C++23 casi completo, Fortran, Ada, Go | C23 y C++23 en buena parte; diagnósticos muy claros | sigue de cerca cada versión de C#, de la que es la implementación de referencia |

El soporte de los estándares cambia con cada versión, y conviene consultar las tablas de soporte de cada proyecto.

**Ejercicio 5.** Características razonables para 2030:

1. **una IR con varios niveles**, al estilo de MLIR, que exprese tensores, ciclos y paralelismo, y se baje a CPU, GPU, NPU o FPGA con un modelo de costos de cada uno;
2. **heurísticas aprendidas** con salvaguardas: modelos que deciden la expansión en línea o la vectorización, pero cuyas decisiones solo cambian el rendimiento, nunca el significado, porque las transformaciones siguen siendo las verificadas;
3. **asistencia por IA en los diagnósticos**: explicar un error y proponer la corrección, sin que la IA genere el código objeto;
4. **seguridad por omisión**: verificación de límites de memoria donde el lenguaje lo permita, mitigaciones contra canales laterales, compilación **reproducible**, que produzca exactamente el mismo binario a partir del mismo fuente para poder auditarlo, y partes críticas verificadas formalmente;
5. **compilación incremental y distribuida** como modo normal, con cachés compartidas;
6. **conciencia de la energía**: optimizar consumo además de tiempo, sobre todo en dispositivos móviles y centros de datos.
