# Introducción a las Ciencias de la Computación - Hilos de ejecución y multi-proceso (threads)

## 9.4 Terminación de ejecución.

---

Iniciar un hilo es fácil; detenerlo correctamente no lo es tanto. Un hilo puede estar a la mitad de modificar una estructura compartida, esperando datos de la red o sosteniendo un candado, y detenerlo bruscamente dejaría el programa en un estado inconsistente. Por eso Java **no ofrece una forma segura de matar un hilo desde fuera**: la terminación es **cooperativa**. Un hilo pide a otro que se detenga, y el otro revisa esa petición en puntos seguros, limpia lo que haga falta y termina. Esta página presenta las formas en que termina un hilo, el mecanismo de interrupción, el cierre de ejecutores y la terminación del programa completo.

### 1. Cómo termina un hilo

Un hilo termina cuando su método `run()` termina, de una de dos maneras:

- **Normalmente**, al llegar al final o ejecutar `return`.
- **Abruptamente**, por una excepción no atrapada. La excepción termina **solo ese hilo**, no el programa: los demás hilos siguen ejecutándose, y la traza se imprime en el error estándar.

```java
public class ExcepcionEnHilo {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> { throw new IllegalStateException("falla en el hilo"); }, "trabajador");
        t.setUncaughtExceptionHandler((hilo, e) ->
                System.out.println("El hilo " + hilo.getName() + " terminó por: " + e.getMessage()));
        t.start();
        t.join();
        System.out.println("main sigue vivo; estado de t: " + t.getState());
    }
}
```

```text
El hilo trabajador terminó por: falla en el hilo
main sigue vivo; estado de t: TERMINATED
```

Un **manejador de excepciones no atrapadas** permite registrar estas fallas en lugar de que pasen inadvertidas. Con ejecutores, la excepción queda guardada en el `Future` y se obtiene con `get()` (subtema 9.2).

### 2. Por qué no existe `stop`

La clase `Thread` tuvo un método `stop()` que detenía el hilo en cualquier punto. Está **obsoleto** desde Java 1.2 y en versiones recientes ya no funciona, porque es intrínsecamente inseguro: al detener el hilo se liberan de golpe todos sus candados, y si estaba a la mitad de una transferencia bancaria, por ejemplo, otros hilos verían el dinero retirado de una cuenta pero no depositado en la otra.

### 3. Interrupción

La interrupción es el mecanismo estándar de cancelación. Cada hilo tiene una **bandera de interrupción**:

- `t.interrupt()` **solicita** a `t` que se detenga, activando su bandera. No lo detiene.
- `Thread.currentThread().isInterrupted()` consulta la bandera del hilo actual.
- Los métodos que bloquean, como `sleep`, `join`, `wait` y `BlockingQueue.take`, al detectar la interrupción **lanzan `InterruptedException`** y desactivan la bandera.

El hilo debe cooperar: revisar periódicamente la bandera en sus ciclos y, al recibir la interrupción, limpiar y terminar.

```java
public class Interrupcion {
    public static void main(String[] args) throws InterruptedException {
        Thread trabajador = new Thread(() -> {
            int ciclos = 0;
            try {
                while (!Thread.currentThread().isInterrupted()) {   // punto de revisión
                    ciclos++;
                    Thread.sleep(10);                               // también responde a la interrupción
                }
            } catch (InterruptedException e) {
                // la interrupción llegó durante sleep: se sale del ciclo
            } finally {
                System.out.println("Limpieza hecha; ciclos completados: " + (ciclos > 0));
            }
        });
        trabajador.start();
        Thread.sleep(100);
        trabajador.interrupt();                                     // solicitud de terminación
        trabajador.join();
        System.out.println("¿Vivo? " + trabajador.isAlive());
    }
}
```

```text
Limpieza hecha; ciclos completados: true
¿Vivo? false
```

**Nunca tragarse la interrupción.** Si un método atrapa `InterruptedException` y no puede terminar el hilo por sí mismo, debe propagarla o **restaurar la bandera** para que el código de más arriba se entere:

```java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();     // se vuelve a activar la bandera
    return;
}
```

### 4. Otras formas de pedir la terminación

**Bandera `volatile`.** Para tareas propias, un atributo `volatile boolean` que el hilo revisa en cada iteración:

```java
class Monitor implements Runnable {
    private volatile boolean activo = true;
    public void detener() { activo = false; }
    public void run() {
        while (activo) { revisarSensores(); }
    }
    private void revisarSensores() { /* trabajo de cada iteración */ }
}
```

Es sencillo, pero tiene una limitación: si el hilo está bloqueado en `sleep` o `take`, no revisará la bandera hasta que despierte. La interrupción sí lo despierta.

**Píldora venenosa.** En el esquema productor y consumidor, el productor coloca en la cola un valor especial que significa "no hay más datos" (subtema 9.3). El consumidor termina ordenadamente después de procesar todo lo anterior.

### 5. Cerrar un ejecutor

Los hilos de un `ExecutorService` no son de servicio: si no se cierra el ejecutor, **el programa no termina**. Hay dos formas de cerrarlo:

| Método                     | Efecto                                                                    |
| -------------------------- | ------------------------------------------------------------------------- |
| `shutdown()`               | no acepta tareas nuevas, pero termina las que están en curso y en cola    |
| `shutdownNow()`            | además, interrumpe las tareas en curso y regresa las que no empezaron     |
| `awaitTermination(t, u)`   | espera a que termine, a lo más el tiempo indicado                         |
| `close()`, desde Java 19   | `shutdown` seguido de esperar a que termine; permite usar `try` con recursos |

El patrón recomendado combina ambas: cierre ordenado con un plazo, y cierre forzado si se excede.

```java
import java.util.concurrent.*;

public class CierreEjecutor {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService ej = Executors.newFixedThreadPool(2);
        ej.submit(() -> System.out.println("tarea corta terminada"));
        ej.submit(() -> {
            try { Thread.sleep(60_000); }                       // tarea muy larga
            catch (InterruptedException e) { System.out.println("tarea larga interrumpida"); }
        });

        ej.shutdown();                                           // no más tareas
        if (!ej.awaitTermination(500, TimeUnit.MILLISECONDS)) {  // plazo de cortesía
            ej.shutdownNow();                                    // interrumpe a las que siguen
            ej.awaitTermination(1, TimeUnit.SECONDS);
        }
        System.out.println("¿Terminado? " + ej.isTerminated());
    }
}
```

```text
tarea corta terminada
tarea larga interrumpida
¿Terminado? true
```

Una tarea individual también se puede cancelar con `future.cancel(true)`, que la interrumpe si ya empezó.

### 6. Terminación del programa

La JVM termina cuando:

1. todos los hilos que **no** son de servicio han terminado; los hilos de servicio se abandonan donde estén, sin ejecutar sus bloques `finally`;
2. algún hilo llama a `System.exit(codigo)`, que termina todo inmediatamente;
3. el sistema operativo envía una señal de terminación, por ejemplo cuando el usuario presiona Ctrl+C.

En los casos 2 y 3 se ejecutan los **ganchos de cierre** registrados, útiles para guardar el estado o cerrar conexiones:

```java
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    System.out.println("Guardando el estado antes de salir...");
    guardarEstado();
}));
```

Los ganchos deben ser rápidos y no depender de otros hilos, que pueden estar en cualquier estado. Si la JVM es terminada a la fuerza, por ejemplo con `kill -9`, no se ejecuta nada: un programa robusto no debe depender de los ganchos para mantener la consistencia de sus datos.

> **Conexión con CC.** La cancelación cooperativa es un principio general de los sistemas concurrentes. Los sistemas operativos usan **señales** para avisar a un proceso que debe terminar, dándole la oportunidad de limpiar, y solo como último recurso lo eliminan a la fuerza. En los servidores y en los contenedores, un **apagado ordenado** deja de aceptar peticiones nuevas, termina las que están en curso y libera los recursos, exactamente el patrón de `shutdown` y `awaitTermination`.

### Ejercicios propuestos

1. Modifique `Interrupcion` quitando el `Thread.sleep(10)` del ciclo. ¿Sigue terminando el hilo? ¿Y si además quita la revisión de `isInterrupted` en la condición del `while`?
2. Escriba un método que atrape `InterruptedException` y no haga nada. Muestre con un programa cómo esto impide que un hilo se detenga al ser interrumpido.
3. Escriba un hilo que muestre un reloj en la consola cada segundo y que termine cuando el usuario escriba `salir`. Implemente la terminación primero con una bandera `volatile` y luego con interrupción.
4. Compruebe que un programa con un `ExecutorService` que no se cierra no termina. Corríjalo con `try` con recursos.
5. Marque un hilo como de servicio, haga que imprima algo en un bloque `finally` después de dormir 5 segundos, y haga que `main` termine de inmediato. ¿Se imprime el mensaje? Explique.
6. Registre un gancho de cierre que imprima un mensaje, y compruebe si se ejecuta al terminar con `System.exit`, con Ctrl+C y al cerrar normalmente.
