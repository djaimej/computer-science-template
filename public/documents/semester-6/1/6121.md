# Ingeniería de Software - Elementos de diseño de sistemas

## 2.1 Características y beneficios del uso de componentes.

---

Un sistema grande no se diseña como una sola pieza, sino como un conjunto de **componentes** que colaboran. Szyperski define un componente de software como una unidad de composición con interfaces especificadas por contrato y dependencias explícitas del contexto, que puede desplegarse de forma independiente y que terceros pueden componer. La idea es tan antigua como la disciplina: McIlroy propuso en la conferencia de la OTAN de 1968 una industria de componentes de software reutilizables, como la de los componentes electrónicos. Este tema describe qué caracteriza a un componente, los beneficios que se buscan al usarlos, las métricas para evaluar sus dependencias y el cálculo económico de la reutilización.

### Características

- **Interfaz explícita:** el componente se usa solo a través de las operaciones que publica, con un contrato que especifica sus precondiciones, sus resultados y sus errores. Su implementación queda oculta.
- **Dependencias explícitas:** declara las interfaces que **requiere** de su entorno, no las implementaciones concretas. En un diagrama de componentes de UML, las interfaces provistas se dibujan como círculos y las requeridas como semicírculos.
- **Independencia de despliegue:** puede compilarse, versionarse y sustituirse por separado, siempre que la nueva versión respete la interfaz.
- **Composición:** se combina con otros componentes sin modificar su código, conectando interfaces requeridas con provistas, a menudo con **inyección de dependencias**: el componente recibe sus colaboradores en lugar de crearlos.
- **Cohesión alta y acoplamiento bajo:** agrupa responsabilidades relacionadas y depende de pocos componentes, a través de interfaces estrechas.

La **inyección de dependencias** tiene un beneficio inmediato en las pruebas: un componente que recibe un reloj y un servicio de notificaciones puede probarse con un reloj falso, para verificar la expiración de un token sin esperar, y con un buzón en memoria en lugar de un servidor de correo.

### Beneficios

- **Reutilización:** un componente bien diseñado se usa en varios sistemas, lo que reduce costos y defectos, porque el código usado muchas veces está más probado.
- **Mantenibilidad:** un cambio dentro de un componente no afecta a los demás mientras su interfaz no cambie.
- **Trabajo en paralelo:** equipos distintos desarrollan componentes distintos contra interfaces acordadas.
- **Sustitución:** un componente puede reemplazarse por otro, comprado, de código abierto o mejorado, que implemente la misma interfaz.
- **Prueba aislada:** cada componente se prueba por separado con dobles de sus dependencias.

Los beneficios no son gratuitos. Construir un componente para que sea reutilizable cuesta más que construirlo para un solo uso: Poulin estima entre 50 y 100 % más, por la generalidad, la documentación y las pruebas adicionales. Y usar un componente ajeno implica depender de su evolución, su licencia y su seguridad (tema 2.5).

### Métricas de dependencias

Martin propone medir la estabilidad de un componente con su **acoplamiento aferente** $C_a,$ el número de componentes que dependen de él, y su **acoplamiento eferente** $C_e,$ el número de componentes de los que depende. La **inestabilidad** es

$$I = \frac{C_e}{C_a + C_e},$$

que vale 0 para un componente del que muchos dependen y que no depende de nadie, y que por eso es difícil de cambiar, y 1 para uno que depende de otros y del que nadie depende. El **principio de dependencias estables** pide que las dependencias apunten hacia componentes más estables, de $I$ mayor a $I$ menor, y el **principio de dependencias acíclicas**, que el grafo de dependencias no tenga ciclos: con un ciclo, ningún componente del ciclo puede construirse, probarse o versionarse por separado.

import hashlib, hmac, secrets

from typing import Protocol, runtime_checkable

# ---------- Ejercicio 1: componentes de un sistema universitario y sus dependencias ----------
componentes = {                                           # componente: interfaces que requiere de otros
    "Estudiantes": [], "Cursos": [], "Pagos": ["Estudiantes"],
    "Matrícula": ["Estudiantes", "Cursos", "Pagos"], "Calificaciones": ["Matrícula"],
    "Reportes": ["Estudiantes", "Cursos", "Calificaciones", "Pagos"], "Usuarios": [],
}
def orden_topologico(g):
    visitado, orden, en_curso = set(), [], set()
    def dfs(n):
        if n in en_curso: raise ValueError(f"ciclo de dependencias en {n}")
        if n in visitado: return
        en_curso.add(n)
        for m in g[n]: dfs(m)
        en_curso.discard(n); visitado.add(n); orden.append(n)
    for n in sorted(g): dfs(n)
    return orden
print("ejercicio 1: orden de construcción:", orden_topologico(componentes))
ca = {c: sum(c in deps for deps in componentes.values()) for c in componentes}   # acoplamiento aferente
ce = {c: len(d) for c, d in componentes.items()}                                   # acoplamiento eferente
print("   inestabilidad I = Ce/(Ca+Ce):", {c: round(ce[c] / (ca[c] + ce[c]), 2) if ca[c] + ce[c] else 0 for c in componentes})
try: orden_topologico(componentes | {"Estudiantes": ["Calificaciones"]})
except ValueError as e: print("   si Estudiantes dependiera de Calificaciones:", e)

# ---------- Ejercicio 2: componente de gestión de usuarios ----------
@runtime_checkable
class Reloj(Protocol):
    def ahora(self) -> float: ...
@runtime_checkable
class Notificador(Protocol):
    def envia(self, destino: str, mensaje: str) -> None: ...
class GestionUsuarios(Protocol):                          # la interfaz que el componente provee
    def registra(self, email: str, password: str, nombre: str) -> str: ...
    def autentica(self, email: str, password: str) -> str | None: ...
    def solicita_recuperacion(self, email: str) -> None: ...
    def restablece(self, token: str, nuevo_password: str) -> bool: ...
    def actualiza_perfil(self, sesion: str, **cambios) -> dict: ...
@dataclass
class Usuario:
    id: str; email: str; sal: bytes; hash_pw: bytes; perfil: dict = field(default_factory=dict)
def deriva(password, sal): return hashlib.scrypt(password.encode(), salt=sal, n=2 ** 14, r=8, p=1)
class UsuariosEnMemoria:
    """Implementa GestionUsuarios. Depende solo de las interfaces Reloj y Notificador, que se inyectan."""
    VIGENCIA = 15 * 60
    def __init__(self, reloj: Reloj, notificador: Notificador, rng=secrets.SystemRandom()):
        self.reloj, self.notificador, self.rng = reloj, notificador, rng
        self.por_email, self.sesiones, self.tokens, self.n = {}, {}, {}, 0
    def _token(self): return "%032x" % self.rng.getrandbits(128)
    def registra(self, email, password, nombre):
        email = email.strip().lower()
        if "@" not in email: raise ValueError("email inválido")
        if email in self.por_email: raise ValueError("el usuario ya existe")
        if len(password) < 10: raise ValueError("la contraseña debe tener al menos 10 caracteres")
        self.n += 1; sal = self.rng.randbytes(16)
        self.por_email[email] = Usuario(f"u{self.n}", email, sal, deriva(password, sal), {"nombre": nombre})
        return f"u{self.n}"
    def autentica(self, email, password):
        u = self.por_email.get(email.strip().lower())
        sal, esperado = (u.sal, u.hash_pw) if u else (b"\0" * 16, b"\0" * 64)   # deriva aunque no exista: mismo tiempo
        if not hmac.compare_digest(esperado, deriva(password, sal)) or not u: return None
        s = self._token(); self.sesiones[s] = u; return s
    def solicita_recuperacion(self, email):
        u = self.por_email.get(email.strip().lower())
        if u:                                             # no revela si el email existe
            t = self._token(); self.tokens[t] = (u, self.reloj.ahora() + self.VIGENCIA)
            self.notificador.envia(u.email, f"token {t}")
    def restablece(self, token, nuevo_password):
        u, vence = self.tokens.pop(token, (None, 0))      # un solo uso
        if not u or self.reloj.ahora() > vence or len(nuevo_password) < 10: return False
        u.sal = self.rng.randbytes(16); u.hash_pw = deriva(nuevo_password, u.sal)
        self.sesiones = {s: v for s, v in self.sesiones.items() if v is not u}   # cierra sesiones abiertas
        return True
    def actualiza_perfil(self, sesion, **cambios):
        u = self.sesiones.get(sesion)
        if not u: raise PermissionError("sesión inválida")
        permitidos = {"nombre", "telefono", "idioma"}
        if not set(cambios) <= permitidos: raise ValueError(f"campos no permitidos: {sorted(set(cambios) - permitidos)}")
        u.perfil.update(cambios); return dict(u.perfil)
class RelojFalso:
    def __init__(self): self.t = 0.0
    def ahora(self): return self.t
class Buzon:
    def __init__(self): self.mensajes = []
    def envia(self, destino, mensaje): self.mensajes.append((destino, mensaje))
import random
reloj, buzon = RelojFalso(), Buzon()
svc = UsuariosEnMemoria(reloj, buzon, rng=random.Random(9))

for intento in (lambda: svc.registra("ana@ejemplo.mx", "otra-contraseña", "Ana"), lambda: svc.registra("sin-arroba", "x" * 12, "X"),
                lambda: svc.registra("b@x.mx", "corta", "B")):
    try: intento()
    except ValueError as e: print("   rechazado:", e)
s = svc.autentica("ana@ejemplo.mx", "contraseña-larga")
print("   autenticación correcta:", s is not None, "| incorrecta:", svc.autentica("ana@ejemplo.mx", "mala"),
      "| inexistente:", svc.autentica("nadie@x.mx", "contraseña-larga"))
print("   perfil:", svc.actualiza_perfil(s, telefono="5551234"))
svc.solicita_recuperacion("ana@ejemplo.mx"); svc.solicita_recuperacion("nadie@x.mx")
token = buzon.mensajes[-1][1].split()[1]
reloj.t = 16 * 60                                         # pasan 16 minutos: el token de 15 expiró
print("   mensajes enviados:", len(buzon.mensajes), "| token expirado:", svc.restablece(token, "nueva-contraseña"))
svc.solicita_recuperacion("ana@ejemplo.mx"); token = buzon.mensajes[-1][1].split()[1]
print("   token vigente:", svc.restablece(token, "nueva-contraseña"), "| reutilizado:", svc.restablece(token, "otra-más-larga"),
      "| sesión anterior cerrada:", s not in svc.sesiones, "| nueva contraseña funciona:", svc.autentica("ana@ejemplo.mx", "nueva-contraseña") is not None)

n_reuso, c_reuso, n_nuevos, c_nuevo, c_base = 5, 2_000, 10, 8_000, 12_000

print(f"   solo por reutilizar: ahorro {ahorro_reuso:,}, ROI sobre lo invertido en reutilizar = {ahorro_reuso / (n_reuso * c_reuso):.0%}")
for extra in (0.5, 1.0):                                  # costo de haber construido esos 5 componentes para reutilizarse

### Ejercicios Propuestos

1. **Identificación de componentes.** Identifica los componentes de un sistema de gestión universitaria que debe manejar la matrícula de estudiantes, la gestión de cursos, las calificaciones, los pagos y los reportes administrativos.

2. **Interfaces.** Diseña las interfaces de un componente de gestión de usuarios que proporcione registro, autenticación, recuperación de contraseña y gestión de perfiles.

3. **Retorno de la inversión.** Un proyecto desarrolla 15 componentes: 5 se reutilizan con un costo de 2 000 cada uno, y 10 se desarrollan desde cero con un costo de 8 000 cada uno. Desarrollar todos desde cero habría costado 12 000 por componente. Calcula el retorno de la inversión,

$$\mathrm{ROI} = \frac{\text{beneficio} - \text{inversión}}{\text{inversión}} \times 100.$$

### Soluciones

**Ejercicio 1.** Cada componente corresponde a una responsabilidad del dominio con datos propios:

- **Estudiantes:** datos personales y académicos;
- **Cursos:** catálogo, grupos, horarios y cupos;
- **Matrícula:** inscripción de un estudiante en un grupo, con reglas de cupo, requisitos y choques de horario;
- **Calificaciones:** evaluaciones de cada matrícula;
- **Pagos:** cargos, pagos y adeudos de cada estudiante;
- **Reportes:** consultas agregadas sobre los demás;
- **Usuarios:** autenticación y permisos, transversal a todos.

Las dependencias van de los componentes de proceso hacia los de datos: Matrícula usa Estudiantes, Cursos y Pagos, para verificar que no haya adeudos; Calificaciones usa Matrícula, y Reportes consulta a todos. El grafo no tiene ciclos y el orden de construcción es el del programa. Estudiantes y Cursos tienen inestabilidad 0: muchos dependen de ellos, y sus interfaces deben ser las más cuidadas y estables; Reportes tiene 1 y puede cambiar libremente. Si Estudiantes dependiera de Calificaciones, por ejemplo para guardar el promedio en el expediente, se formaría un ciclo; la solución es que Calificaciones **publique** el promedio, o que el expediente lo consulte en Reportes, invirtiendo la dependencia.

**Ejercicio 2.** La interfaz provista tiene cinco operaciones: `registra(email, password, nombre)`, que devuelve el identificador; `autentica(email, password)`, que devuelve una sesión o nada; `solicita_recuperacion(email)`; `restablece(token, nuevo_password)`, y `actualiza_perfil(sesion, **cambios)`. Las interfaces requeridas son un **reloj**, para la expiración, y un **notificador**, para enviar el token. El contrato incluye las decisiones de seguridad, que forman parte de la interfaz aunque no se vean en las firmas:

- las contraseñas se guardan con una función de derivación lenta y con sal, scrypt en el programa, y se comparan en tiempo constante; nunca en claro;
- la autenticación responde lo mismo, y tarda lo mismo, para un usuario inexistente y para una contraseña incorrecta, y la solicitud de recuperación no revela si el correo existe, para no permitir enumerar cuentas;
- el token de recuperación es aleatorio, de un solo uso y expira a los 15 minutos, y restablecer la contraseña cierra las sesiones abiertas;
- el perfil solo acepta campos permitidos, de modo que no se puede cambiar el email o el rol por esa vía.

La prueba del programa ejercita cada regla con el reloj falso: avanza 16 minutos y el token ya no sirve.

**Ejercicio 3.** El enunciado admite dos lecturas, y conviene decir cuál se usa:

1. **Todo el proyecto:** el costo real es de $5 \cdot 2\,000 + 10 \cdot 8\,000 = 90\,000,$ el costo sin reutilizar sería de $15 \cdot 12\,000 = 180\,000,$ y el ROI es $(180\,000 - 90\,000) / 90\,000 = 100\,\%.$ Pero esta cuenta atribuye a la reutilización también el ahorro de los 10 componentes nuevos, que cuestan 8 000 en lugar de 12 000 por otras razones.
2. **Solo la reutilización:** cada componente reutilizado ahorra $12\,000 - 2\,000 = 10\,000,$ en total 50 000, con una inversión de 10 000: un ROI de 500 %.

Ninguna de las dos incluye el costo de haber construido esos componentes para que fueran reutilizables. Si eso costó entre 50 y 100 % más, entre 30 000 y 60 000, se recupera en una o dos reutilizaciones como esta. La reutilización es rentable cuando el componente se usa varias veces, y por eso conviene invertir en ella solo en los componentes con demanda probable.
