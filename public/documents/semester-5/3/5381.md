# Fundamentos de Bases de Datos - Integridad

## 8.1 Integridad de Entidad.

---

Las **restricciones de integridad** son las condiciones que toda instancia válida de la base debe cumplir; el SMBD las verifica en cada modificación y rechaza las que las violarían. Se agrupan en cuatro clases, que son los temas de esta unidad: de **entidad** (este tema), de **dominio** (8.2), **referencial** (8.3) y **de usuario** o semánticas (8.4). La integridad de entidad garantiza que cada fila de una tabla se pueda identificar: que tenga una clave primaria, que esa clave no se repita y que no sea nula.

### Definición

Sea $R$ con clave primaria $PK.$ La **regla de integridad de entidad** exige que, en toda instancia $r$ de $R,$

$$\forall t \in r: \; \forall A \in PK: \; t[A] \text{ no es nulo},$$

y la **restricción de clave** exige que

$$\forall t_1, t_2 \in r: \; t_1[PK] = t_2[PK] \;\Rightarrow\; t_1 = t_2.$$

La primera se justifica porque un nulo en la clave significa que no se sabe qué entidad representa la fila, y entonces no se puede hacer referencia a ella, ni distinguirla de otra, ni actualizarla con seguridad. Para una clave compuesta, **ninguno** de sus atributos puede ser nulo, no solo la combinación. Las claves alternativas, declaradas `UNIQUE`, no tienen la restricción de no nulidad salvo que se declare: SQL permite varios nulos en una columna `UNIQUE`, porque dos nulos no se consideran iguales (SQL Server es la excepción, y PostgreSQL 15 agregó `UNIQUE NULLS NOT DISTINCT`).

### Implementación en SQL

```sql
CREATE TABLE empleado (
    id_empleado INTEGER NOT NULL,
    nombre      VARCHAR(50) NOT NULL,
    CONSTRAINT pk_empleado PRIMARY KEY (id_empleado)
);
CREATE TABLE matricula (
    id_estudiante INTEGER NOT NULL,
    id_curso      INTEGER NOT NULL,
    semestre      CHAR(6) NOT NULL,
    PRIMARY KEY (id_estudiante, id_curso, semestre)
);
```

`PRIMARY KEY` implica `UNIQUE` y `NOT NULL` en el estándar, y el SMBD crea un índice para verificar la unicidad rápido. Nombrar la restricción ayuda a leer los mensajes de error y a eliminarla después. Para generar claves, el estándar ofrece `GENERATED ALWAYS AS IDENTITY`; PostgreSQL también `SERIAL`, MySQL `AUTO_INCREMENT` y SQLite `INTEGER PRIMARY KEY`.

SQLite tiene dos peculiaridades que conviene conocer. Por compatibilidad con versiones antiguas, una clave primaria que **no** sea `INTEGER PRIMARY KEY` admite nulos, salvo que se declare `NOT NULL` o la tabla sea `STRICT`. Y una columna `INTEGER PRIMARY KEY` es un alias del identificador interno de la fila: insertar un nulo en ella no es un error, sino que genera un número nuevo.

### Claves naturales y suplentes

Una **clave natural** tiene significado en el dominio: el ISBN de un libro, el RFC o la CURP de una persona, el código de un aeropuerto. Una **clave suplente** (*surrogate*) es un identificador sin significado que genera el sistema, como un entero consecutivo o un UUID.

| Aspecto                 | Natural                                                 | Suplente                                                 |
| ----------------------- | ------------------------------------------------------- | -------------------------------------------------------- |
| Estabilidad             | Puede cambiar (error de captura, cambio de norma)       | No cambia nunca                                          |
| Existencia              | Puede faltar al registrar (un libro antiguo sin ISBN)   | Siempre existe                                           |
| Tamaño en claves foráneas | Variable, a veces largo                                | Corto y fijo                                             |
| Significado             | Visible, útil al consultar                              | Ninguno: requiere reunir para saber qué es              |
| Duplicados del mundo real | Los impide                                             | No los impide por sí sola                                |

La práctica habitual combina ambas: una clave suplente como clave primaria y la natural como clave alternativa `UNIQUE NOT NULL`. Así las claves foráneas usan el identificador estable y la base sigue impidiendo, por ejemplo, dos libros con el mismo ISBN. La última fila de la tabla es la razón: sin la restricción `UNIQUE` sobre la clave natural, una clave suplente permite registrar dos veces la misma entidad con números distintos.

### Ejercicios Propuestos

1. **Diseño.** Diseña las tablas de una biblioteca con libros, que deben tener un ISBN único, autores, que pueden tener varios libros, y préstamos, en la que un libro se puede prestar muchas veces.

2. **Problemas.** Identifica los problemas de integridad de entidad del siguiente código:

    ```sql
    CREATE TABLE Empleado (id_empleado INT, nombre VARCHAR(50), departamento VARCHAR(50));
    INSERT INTO Empleado VALUES (NULL, 'Juan Pérez', 'Ventas');
    INSERT INTO Empleado VALUES (101, 'María López', 'Marketing');
    INSERT INTO Empleado VALUES (101, 'Carlos Ruiz', 'TI');
    ```

3. **Corrección.** Corrige el esquema del ejercicio 2 para garantizar la integridad de entidad.

4. **Repaso.** ¿Por qué importa la integridad de entidad? ¿Qué pasa al insertar una fila con nulos en la clave primaria? ¿Cómo se aplica a las claves compuestas? ¿Qué diferencia hay entre una clave natural y una suplente? ¿Qué mecanismos da SQL para garantizarla?

### Soluciones

**Ejercicio 1.** `libro(id_libro, isbn, titulo)` con `id_libro` como clave suplente e `isbn UNIQUE NOT NULL`; `autor(id_autor, nombre)`; `libro_autor(id_libro, id_autor)` con clave compuesta, que impide registrar dos veces al mismo autor en un libro y no admite nulos en ninguna de sus partes; `prestamo(id_prestamo, id_libro, socio, fecha_prestamo, fecha_devolucion)` con clave suplente, porque el mismo libro se presta muchas veces, y una clave alternativa `(id_libro, fecha_prestamo)` si la regla es que un ejemplar no se presta dos veces el mismo día. La clave suplente del libro paga su costo al corregir un ISBN mal capturado: solo cambia una fila de `libro`, y los préstamos y autorías siguen ligados.

**Ejercicio 2.** La tabla no tiene clave primaria, y por eso:

- Acepta un empleado con identificador **nulo**: Juan no se puede buscar por su clave, porque `id_empleado = NULL` nunca es verdadero, ni ser referenciado desde otra tabla.
- Acepta dos empleados con el identificador **101**: una consulta por ese identificador devuelve a María y a Carlos, un `UPDATE ... WHERE id_empleado = 101` los modifica a los dos, y una clave foránea hacia 101 sería ambigua.
- Además, nada impide registrar dos veces a la misma persona con identificadores distintos; eso requeriría una clave natural adicional.

**Ejercicio 3.**

```sql
CREATE TABLE empleado (
    id_empleado  INTEGER NOT NULL,
    nombre       VARCHAR(50) NOT NULL,
    departamento VARCHAR(50) NOT NULL,
    CONSTRAINT pk_empleado PRIMARY KEY (id_empleado)
);
```

Con ella, la tercera inserción se rechaza por clave repetida. La primera se rechaza en el estándar por el nulo; en SQLite, como `id_empleado` es `INTEGER PRIMARY KEY`, el nulo se reemplaza por un número nuevo y Juan recibe el 1, como muestra el programa. Si se quiere que SQLite rechace el nulo, la columna debe declararse con otro tipo, como `INT`, o la tabla como `STRICT`. Para aplicar la corrección sobre los datos existentes, primero hay que resolver los conflictos, porque `ALTER TABLE ... ADD PRIMARY KEY` falla con nulos o repetidos: asignar un identificador a Juan y otro a Carlos, después de comprobar con consultas cuáles son. Lo mejor es que el sistema genere los identificadores, con `GENERATED ALWAYS AS IDENTITY`, para que no se capturen a mano. El departamento debería ser una clave foránea a una tabla de departamentos (tema 8.3).

**Ejercicio 4.** Importa porque sin ella no se puede identificar, referenciar ni actualizar una fila sin ambigüedad. Una inserción con nulo en la clave primaria se rechaza, salvo la excepción de SQLite descrita. En una clave compuesta, ningún atributo puede ser nulo, y lo que no se repite es la combinación: dos matrículas pueden compartir estudiante o curso, pero no los tres valores. Una clave natural tiene significado en el dominio y puede cambiar; una suplente no tiene significado y no cambia, y lo habitual es usar la suplente como primaria y declarar la natural `UNIQUE`. Los mecanismos son `PRIMARY KEY`, `UNIQUE`, `NOT NULL` y la generación automática de identificadores.
