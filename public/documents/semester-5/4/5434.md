# Lenguajes de Programación - Paradigma funcional

## 3.4 Estilos de tipado: tipado dinámico vs. tipado estático.

---

Todo lenguaje de alto nivel distingue tipos de valores: no tiene sentido sumar una cadena con una función. La diferencia entre los lenguajes está en **cuándo** se verifica que las operaciones se apliquen a valores del tipo correcto. Con **tipado estático**, un verificador analiza el programa antes de ejecutarlo y rechaza los que podrían cometer un error de tipos. Con **tipado dinámico**, cada operación revisa el tipo de sus operandos al ejecutarse. Ambos estilos tienen ventajas reales, y los lenguajes actuales tienden a combinarlos. Este tema compara los dos estilos, aclara los términos que se suelen confundir con ellos y muestra con un mismo lenguaje qué detecta cada uno.

### Tipado estático

El tipo es una propiedad de las **expresiones** y las **variables**, que el compilador determina a partir del texto (temas 3.3 y 3.7). Un programa mal tipado no se ejecuta. Ejemplos: C, Java, C#, Go, Rust, ML, Haskell, Scala, TypeScript.

Ventajas:

- Los errores de tipos se detectan **antes** de ejecutar, en todas las ramas, incluidas las que las pruebas no cubren.
- Los tipos documentan las interfaces y permiten que las herramientas completen código, naveguen y refactoricen con seguridad.
- El compilador puede generar código más eficiente, porque conoce la representación de cada valor.

Desventajas:

- Rechaza algunos programas que no fallarían nunca, como un condicional con ramas de tipos distintos cuya rama "mala" nunca se toma. Todo sistema de tipos decidible es **conservador**, por el teorema de Rice.
- Exige anotaciones, menos con inferencia de tipos, y a veces formas indirectas de expresar código genérico.

### Tipado dinámico

El tipo es una propiedad de los **valores**: cada valor lleva una etiqueta con su tipo, y las operaciones la revisan. Ejemplos: LISP, Scheme, Smalltalk, Python, Ruby, JavaScript, Erlang.

Ventajas:

- Acepta todo programa que no falle al ejecutarse, y permite estructuras heterogéneas y metaprogramación con menos ceremonia.
- Es rápido de escribir y de modificar, y se presta a la exploración y a los prototipos.
- El **tipado de pato** (*duck typing*): un objeto sirve si tiene los métodos que se usan, sin declarar una interfaz.

Desventajas:

- Los errores aparecen solo al ejecutar la línea que los contiene, posiblemente en producción.
- Hay que compensar con más pruebas, y las herramientas saben menos del código.
- El costo de revisar las etiquetas en cada operación, que los compiladores en tiempo de ejecución reducen especializando el código.

### Términos que se confunden

- **Estático o dinámico** dice cuándo se verifica. **Fuerte o débil** dice si el lenguaje impide las operaciones sin sentido o las realiza con **conversiones implícitas**: Python es dinámico y fuerte, porque `"5" + 3` es un error; JavaScript es dinámico y débil, porque `"5" + 3` da `"53"` y `"5" - 3` da `2`; C es estático y débil, porque permite tratar cualquier memoria como cualquier tipo con un *cast*. Los términos fuerte y débil no tienen una definición única.
- **Seguro** (*type safe*) significa que ningún programa aceptado puede realizar una operación sin sentido sobre la memoria: Java, Python, Haskell y Rust lo son; C y C++ no.
- **Explícito o inferido** dice si el programador escribe los tipos: Haskell y OCaml son estáticos con inferencia casi completa; Java es estático con anotaciones obligatorias en las firmas.
- **Nominal o estructural** dice si dos tipos son compatibles por su nombre, como en Java, o por su forma, como en TypeScript y Go con sus interfaces.

### Tipado gradual

El **tipado gradual** (Siek y Taha, 2006) permite mezclar código con y sin tipos en un mismo programa: las partes anotadas se verifican estáticamente, y en la frontera con las no anotadas se insertan verificaciones dinámicas. TypeScript sobre JavaScript, las anotaciones de Python con verificadores como mypy, Hack sobre PHP y Typed Racket siguen esta idea, en distintas variantes: TypeScript y mypy borran los tipos al ejecutar y no insertan verificaciones, de modo que son verificadores opcionales y no garantizan la seguridad en la frontera.

| Error                                   | Estático (Java, Haskell)          | Dinámico (Python)           |
| --------------------------------------- | --------------------------------- | --------------------------- |
| `"5" + 3`                               | Haskell, al compilar; Java da `"53"` | Al ejecutar: `TypeError`    |
| Función no definida                     | Al compilar                       | Al ejecutar esa línea       |
| Índice fuera de rango                   | Al ejecutar, en ambos             | Al ejecutar: `IndexError`   |
| Método inexistente                      | Al compilar                       | Al ejecutar: `AttributeError` |

# expresiones: ("int", n) ("str", s) ("add", a, b) ("concat", a, b) ("if", c, a, b), con c entero (0 es falso)
def check(e):
    """Verificación estática: devuelve "Int", "Str" o None, sin ejecutar nada."""
    k = e[0]
    if k == "int": return "Int"
    if k == "str": return "Str"
    if k in ("add", "concat"):
        a, b = check(e[1]), check(e[2])
        esperado = "Int" if k == "add" else "Str"
        return esperado if a == b == esperado else None
    if k == "if":
        c, a, b = check(e[1]), check(e[2]), check(e[3])
        return a if c == "Int" and a is not None and a == b else None
def evalua(e):
    """Verificación dinámica: cada operación revisa el tipo de sus operandos al ejecutarse."""
    k = e[0]
    if k in ("int", "str"): return e[1]
    if k in ("add", "concat"):
        a, b = evalua(e[1]), evalua(e[2])
        tipo = int if k == "add" else str
        if not (isinstance(a, tipo) and isinstance(b, tipo)): raise TypeError(f"{k} con {type(a).__name__} y {type(b).__name__}")
        return a + b
    if k == "if":
        c = evalua(e[1])
        if not isinstance(c, int): raise TypeError("condición no entera")
        return evalua(e[2]) if c else evalua(e[3])
def txt(e):
    k = e[0]
    if k == "int": return str(e[1])
    if k == "str": return repr(e[1])
    if k == "add": return f"{txt(e[1])} + {txt(e[2])}"
    if k == "concat": return f"{txt(e[1])} ++ {txt(e[2])}"
    return f"if {txt(e[1])} then {txt(e[2])} else {txt(e[3])}"
programas = [("add", ("int", 2), ("int", 3)),
             ("concat", ("str", "ab"), ("str", "cd")),
             ("add", ("int", 2), ("str", "3")),
             ("if", ("int", 1), ("int", 10), ("add", ("int", 1), ("str", "x"))),     # error en la rama que no se toma
             ("if", ("int", 0), ("int", 10), ("str", "diez")),                     # ramas de tipos distintos
             ("if", ("str", "sí"), ("int", 1), ("int", 2))]
print("ejercicio 4:")

    except TypeError as err: dinamico = f"error: {err}"
    print(f"   {txt(p)}\n      estático: {estatico or 'rechazado'} | dinámico: {dinamico}")

### Ejercicios Propuestos

1. **Errores.** Para cada fragmento, indica cuándo se detectaría el error con tipado estático y con tipado dinámico: `"5" + 3`, la llamada a una función no definida, `array[10]` sobre un arreglo de 5 elementos y `objeto.metodo_inexistente()`.

2. **Conversión.** Escribe en Haskell, con tipos, la función de Python

    ```python
    def process_data(data):
        return data.upper() + str(len(data))
    ```

3. **Casos.** Analiza las ventajas y desventajas de cada estilo para prototipos, sistemas críticos, guiones de automatización y bases de código empresariales grandes.

4. **Verificador.** Implementa `checkType :: Expr -> Maybe Type` para `data Expr = LitInt Int | LitStr String | Add Expr Expr | Concat Expr Expr | If Expr Expr Expr`.

### Soluciones

**Ejercicio 1.** Es la tabla de la sección de tipado gradual, que el programa confirma para Python.

- **`"5" + 3`:** Python lo rechaza al ejecutar, con `TypeError`, porque no convierte implícitamente entre cadenas y números; la conversión se pide con `str(3)` o `int("5")`. Haskell lo rechaza al compilar. Java lo **acepta**: el operador `+` con una cadena convierte el otro operando y concatena, y da `"53"`, igual que JavaScript.
- **Función no definida:** un compilador estático la rechaza siempre. Python solo busca el nombre al ejecutar la línea: el programa muestra que la función que la contiene funciona mientras no se tome esa rama. Es la razón por la que en un lenguaje dinámico la cobertura de las pruebas importa tanto.
- **`array[10]`:** casi ningún sistema de tipos lo detecta, porque el tamaño del arreglo y el valor del índice se conocen al ejecutar; se detecta al ejecutar en Java, Python y Haskell, y en C no se detecta y el programa lee memoria ajena. Los **tipos dependientes**, como los de Idris o Agda, sí pueden expresar "un índice menor que la longitud".
- **Método inexistente:** el compilador estático lo rechaza, porque conoce la clase del objeto; Python lanza `AttributeError` al ejecutar.

**Ejercicio 2.**

```haskell
import Data.Char (toUpper)

processData :: String -> String
processData d = map toUpper d ++ show (length d)
```

La versión de Haskell fija el tipo del argumento como `String`; la de Python acepta cualquier objeto con un método `upper` que devuelva algo concatenable con una cadena, y con `len`. El programa lo muestra: falla con una lista al ejecutar, y funciona con un objeto propio que tiene esos dos métodos. Para expresar esa generalidad en un lenguaje estático hace falta una **clase de tipos** o una interfaz: en Haskell, `class Gritable a where upper :: a -> String`; en Python, con anotaciones, un `Protocol`.

**Ejercicio 3.**

- **Prototipos:** el dinámico es más rápido para explorar, porque el esquema de los datos y las interfaces cambian a cada paso. Con inferencia de tipos, como en OCaml o Haskell, la diferencia se reduce.
- **Sistemas críticos:** el estático, por las garantías antes de ejecutar; en el extremo, con herramientas de verificación, como SPARK Ada en aviación o Rust para la seguridad de la memoria. Las pruebas, por muchas que sean, no cubren todas las rutas.
- **Guiones de automatización:** el dinámico, por la brevedad y porque el programa es corto, lo usa su autor y un error se ve de inmediato.
- **Bases de código grandes:** el estático, o el gradual, porque los tipos son documentación verificada y permiten refactorizar con seguridad. La migración de grandes bases de JavaScript a TypeScript y de Python a Python con anotaciones muestra que, a partir de cierto tamaño, las organizaciones agregan tipos a sus lenguajes dinámicos.

**Ejercicio 4.**

```haskell
data Type = TInt | TStr deriving Eq

checkType :: Expr -> Maybe Type
checkType (LitInt _)   = Just TInt
checkType (LitStr _)   = Just TStr
checkType (Add a b)    = do { TInt <- checkType a; TInt <- checkType b; Just TInt }
checkType (Concat a b) = do { TStr <- checkType a; TStr <- checkType b; Just TStr }
checkType (If c a b)   = do { TInt <- checkType c; ta <- checkType a; tb <- checkType b
                            ; if ta == tb then Just ta else Nothing }
```

El enunciado no tiene booleanos, así que la condición se toma entera, con 0 como falso. La función del programa es la misma en Python. La comparación de los seis programas muestra las dos caras del tipado estático: rechaza `2 + '3'` y `if 'sí' then 1 else 2` sin ejecutarlos, igual que el evaluador dinámico al ejecutarlos; pero rechaza también `if 1 then 10 else 1 + 'x'`, cuya rama con error nunca se ejecuta, e `if 0 then 10 else 'diez'`, que el evaluador dinámico ejecuta sin problema. Son programas sin errores de tipos al ejecutarse que el verificador estático, conservador, no acepta.
