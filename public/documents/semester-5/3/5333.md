# Fundamentos de Bases de Datos - Modelado de bases de datos usando el modelo entidad/relación

## 3.3 Especificación de restricciones.

---

Las restricciones en el modelo Entidad/Relación son reglas que limitan los valores válidos que pueden tomar los datos, garantizando la integridad, consistencia y corrección de la información almacenada. Estas restricciones definen las reglas de negocio que deben cumplirse en todo momento.

### Tipos de Restricciones en el Modelo E/R

#### Restricciones Estructurales

##### Restricciones de Cardinalidad

**Definición:** Especifican el número mínimo y máximo de instancias de una entidad que pueden asociarse con instancias de otra entidad mediante una relación.

**Notación:** (min, max) donde:

- min: participación mínima (0 o 1)
- max: participación máxima (1 o N)

**Ejemplos:**

- (1,1): Participación obligatoria, exactamente una instancia
- (0,1): Participación opcional, máximo una instancia
- (1,N): Participación obligatoria, una o muchas instancias
- (0,N): Participación opcional, cero o muchas instancias

##### Restricciones de Existencia

**Definición:** Especifican dependencias existenciales entre entidades, particularmente para entidades débiles.

**Fórmula de dependencia existencial:**

$$∀e_w ∈ E_w, ∃!e_s ∈ E_s \text{ tal que } e_w \text{ depende de } e_s$$

Donde:

- $E_w$: Conjunto de entidades débiles
- $E_s$: Conjunto de entidades fuertes

#### Restricciones de Integridad

##### Restricciones de Clave

**Definición:** Garantizan la unicidad e identificación de instancias de entidades.

**Tipos:**

- **Integridad de entidad:** Ningún atributo de clave primaria puede ser nulo
- **Integridad referencial:** Los valores de clave foránea deben existir en la entidad referenciada o ser nulos

**Fórmula de integridad referencial:**
$$∀t ∈ R[FK], ∃s ∈ S[PK] \text{ tal que } t[FK] = s[PK] ∨ t[FK] = NULL$$

##### Restricciones de Dominio

**Definición:** Limitan los valores que pueden tomar los atributos.

**Ejemplos:**

- Restricciones de tipo de datos: `edad INT CHECK (edad >= 0 AND edad <= 150)`
- Restricciones de formato: `email VARCHAR CHECK (email LIKE '%@%.%')`
- Restricciones de enumeración: `estado ENUM('activo', 'inactivo', 'pendiente')`

#### Restricciones Semánticas

##### Restricciones de Disjunción

**Definición:** Especifican que las instancias de subtipos deben ser mutuamente excluyentes.

**Ejemplo:** Una persona no puede ser同时empleado y cliente simultáneamente si existe restricción de disjunción.

##### Restricciones de Completitud

**Definición:** Especifican si todas las instancias de una superclase deben pertenecer a alguna subclase.

**Tipos:**

- **Completitud total:** Cada instancia de la superclase debe pertenecer al menos a una subclase
- **Completitud parcial:** Las instancias de la superclase pueden no pertenecer a ninguna subclase

### Especificación Formal de Restricciones

#### Notación para Restricciones Complejas

**Usando lógica de predicados:**
$$∀e ∈ Empleado, ∃d ∈ Departamento \text{ tal que } trabaja\_en(e, d)$$
$$∀p ∈ Proyecto, ∃e ∈ Empleado \text{ tal que } coordina(e, p)$$

**Usando cálculo relacional de tuplas:**
$$∀t ∈ trabaja\_en, ∃s ∈ Empleado \text{ tal que } t[id_emp] = s[id_emp]$$
$$∀t ∈ trabaja\_en, ∃u ∈ Departamento \text{ tal que } t[id_depto] = u[id_depto]$$

#### Restricciones de Aserción

**Definición:** Condiciones que deben cumplirse siempre en la base de datos.

**Ejemplo:** "El salario de un empleado no puede ser mayor que el salario de su supervisor"

**Expresión formal:**
$$∀e1, e2 ∈ Empleado, (supervisa(e2, e1) → salario(e1) ≤ salario(e2))$$

### Ejemplos de Representación Gráfica

#### Diagrama E/R con Restricciones de Cardinalidad

```
    EMPLEADO (1,1) -- trabaja_en -- (1,N) DEPARTAMENTO
    │
    │
    dirige (0,1)
    │
    │
    DEPARTAMENTO (1,1)
```

**Leyenda:**

- Rectángulo: Entidad
- Rombo: Relación
- Línea continua: Participación obligatoria
- Línea discontinua: Participación opcional
- (min,max): Cardinalidad

#### Esquema de Entidades con Restricciones

```
ENTIDAD: EMPLEADO
ATRIBUTOS:
  id_emp: INT (PK, NOT NULL)
  nombre: VARCHAR(100) (NOT NULL)
  salario: DECIMAL(10,2) (CHECK > 0)
  fecha_contrato: DATE (NOT NULL)

ENTIDAD: DEPARTAMENTO
ATRIBUTOS:
  id_depto: INT (PK, NOT NULL)
  nombre: VARCHAR(50) (NOT NULL)
  presupuesto: DECIMAL(12,2) (CHECK >= 0)

RELACIÓN: trabaja_en
ENTIDADES: EMPLEADO - DEPARTAMENTO
CARDINALIDAD: (1,1) - (1,N)
RESTRICCIONES:
  - Un empleado trabaja en exactamente un departamento
  - Un departamento tiene al menos un empleado

RELACIÓN: dirige
ENTIDADES: EMPLEADO - DEPARTAMENTO
CARDINALIDAD: (0,1) - (1,1)
RESTRICCIONES:
  - Un departamento tiene exactamente un director
  - Un empleado dirige como máximo un departamento
```

### Ejercicios Propuestos

#### Ejercicio 1: Especificación Formal

Para un sistema de reservas de hotel, escriba las restricciones formales para:
a) Una habitación no puede estar double reservada para las mismas fechas
b) El precio de la habitación debe ser positivo
c) La fecha de salida debe ser posterior a la fecha de entrada

Exprese cada restricción en notación matemática y en lenguaje natural.

#### Ejercicio 2: Diseño con Restricciones

Diseñe un esquema E/R para un sistema bancario que incluya:

- Cuentas, clientes, transacciones y sucursales
- Restricciones:
  - Una cuenta debe tener al menos un titular
  - El saldo nunca puede ser negativo
  - Las transacciones deben tener un monto positivo
  - Cada cuenta pertenece a exactamente una sucursal

Incluya la especificación formal de al menos tres restricciones.

#### Ejercicio 3: Identificación de Restricciones

Analice el siguiente caso y identifique todas las restricciones implícitas:

"En una empresa, cada empleado pertenece a un departamento y tiene un supervisor que también es empleado. Los proyectos son asignados a departamentos y cada proyecto tiene un empleado líder. Los empleados pueden trabajar en múltiples proyectos."

Liste al menos 5 restricciones, clasificándolas por tipo y proporcionando su especificación formal.

### Técnicas de Verificación de Restricciones

#### Validación de Consistencia

**Métodos para verificar restricciones:**

1. **Análisis de integridad referencial:** Verificar que no existan referencias huérfanas
2. **Comprobación de cardinalidades:** Validar que las multiplicidades se cumplen
3. **Verificación de dominios:** Confirmar que los valores están en los rangos permitidos

#### Herramientas Formales

**Uso de lógica para verificación:**

- **Lógica de predicados:** Para expresar restricciones complejas
- **Álgebra relacional:** Para verificar consistencia de operaciones
- **Cálculo relacional:** Para validar consultas contra restricciones

**Ejemplo de verificación formal:**
Para la restricción "Un empleado no puede ser su propio supervisor":

$$∀e ∈ Empleado, ¬supervisa(e, e)$$

### Implementación en Sistemas de Gestión de Bases de Datos

#### Conversión a DDL SQL

**Ejemplo de mapeo de restricciones E/R a SQL:**

```sql
-- Restricción de clave primaria
CREATE TABLE Empleado (
    id_emp INT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    salario DECIMAL(10,2)
);

-- Restricción de integridad referencial
CREATE TABLE Departamento (
    id_depto INT PRIMARY KEY,
    id_director INT,
    FOREIGN KEY (id_director) REFERENCES Empleado(id_emp)
);

-- Restricción de dominio
CREATE TABLE Producto (
    id_producto INT PRIMARY KEY,
    precio DECIMAL(10,2) CHECK (precio > 0),
    categoria VARCHAR(50) CHECK (categoria IN ('Electrónicos', 'Ropa', 'Alimentos'))
);

-- Restricción de aserción compleja (implementación varía por SGBD)
CREATE ASSERTION salario_supervisor CHECK (
    NOT EXISTS (
        SELECT 1 FROM Empleado e, Empleado s
        WHERE e.supervisor_id = s.id_emp
        AND e.salario > s.salario
    )
);
```

### Caso de Estudio: Sistema de Gestión de Proyectos

```
ENTIDAD: EMPLEADO
ATRIBUTOS:
  id_emp: INT (PK)
  nombre: VARCHAR(100) (NOT NULL)
  salario: DECIMAL(10,2) (CHECK > 0)
  id_depto: INT (FK)
  id_supervisor: INT (FK)

ENTIDAD: PROYECTO
ATRIBUTOS:
  id_proyecto: INT (PK)
  nombre: VARCHAR(100) (NOT NULL)
  fecha_inicio: DATE (NOT NULL)
  fecha_fin: DATE (CHECK fecha_fin > fecha_inicio)
  presupuesto: DECIMAL(12,2) (CHECK >= 0)

ENTIDAD: ASIGNACION
ATRIBUTOS:
  id_asignacion: INT (PK)
  id_emp: INT (FK, NOT NULL)
  id_proyecto: INT (FK, NOT NULL)
  fecha_inicio: DATE (NOT NULL)
  fecha_fin: DATE (CHECK fecha_fin >= fecha_inicio)
  horas_asignadas: DECIMAL(5,2) (CHECK > 0)

ENTIDAD: DEPARTAMENTO
ATRIBUTOS:
  id_depto: INT (PK)
  nombre: VARCHAR(50) (NOT NULL)

RESTRICCIONES ESPECÍFICAS:
1. supervisor_valido: ∀e ∈ EMPLEADO, ¬supervisa(e, e)
2. fechas_validas: ∀p ∈ PROYECTO, p.fecha_fin > p.fecha_inicio
3. solapamiento_asignaciones: Un empleado no puede tener asignaciones solapadas

```

### Best Practices para Especificación de Restricciones

1. **Documentación completa:** Registrar todas las restricciones con descripción clara
2. **Consistencia:** Mantener coherencia entre restricciones
3. **Verificabilidad:** Asegurar que las restricciones puedan ser validadas
4. **Mantenibilidad:** Organizar las restricciones por categorías y prioridades
5. **Performance:** Considerar el impacto en el rendimiento al implementar restricciones complejas
