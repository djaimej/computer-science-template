# Fundamentos de Bases de Datos - Lenguaje de consulta SQL

## 6.4 Actualizaciones.

---

Las sentencias de modificación de SQL (`INSERT`, `UPDATE`, `DELETE` y `MERGE`) cambian el estado de la base de datos. Igual que `SELECT`, son **declarativas** y trabajan sobre **conjuntos**: un `UPDATE` describe qué filas cambian y cómo, y el SMBD lo aplica a todas a la vez, como una sola operación atómica que respeta las restricciones de integridad. Este tema presenta las cuatro sentencias, las actualizaciones que dependen de otras tablas, el papel de las transacciones y las restricciones, y los errores más comunes.

### INSERT

```sql
INSERT INTO productos (nombre, precio, stock) VALUES ('Lámpara', 450, 10), ('Foco', 35, 200);
INSERT INTO historico SELECT * FROM ventas WHERE fecha < '2026-01-01';
```

Conviene nombrar siempre las columnas: así la sentencia no se rompe cuando se agrega una columna a la tabla. Las columnas omitidas reciben su valor `DEFAULT` o nulo. Para insertar o actualizar según exista la fila, SQL:2003 define `MERGE`, y PostgreSQL y SQLite ofrecen `INSERT ... ON CONFLICT (clave) DO UPDATE SET ...`, llamado **upsert**.

### UPDATE

```sql
UPDATE productos SET precio = precio * 1.08, fecha_actualizacion = CURRENT_DATE
WHERE categoria = 'Electrónicos';
```

Todas las expresiones de `SET` se evalúan con los valores **anteriores** de la fila: `SET a = b, b = a` intercambia dos columnas. La sentencia es atómica: si una sola fila viola una restricción, ninguna cambia. Sin `WHERE`, cambia **todas** las filas de la tabla.

Una actualización puede depender de otras tablas de dos maneras: con una **subconsulta correlacionada** en `SET` o en `WHERE`, que es estándar, o con `UPDATE ... FROM`, una extensión de PostgreSQL, SQL Server y SQLite que reúne la tabla con otra y usa sus columnas. Con `FROM`, si una fila de la tabla se reúne con varias filas de la otra, el resultado es indefinido; por eso conviene reunir con una subconsulta que ya esté agregada, una fila por clave.

### DELETE

```sql
DELETE FROM ventas WHERE fecha < '2020-01-01';
```

Las claves foráneas determinan qué pasa con las filas que hacen referencia a las borradas: `RESTRICT` o `NO ACTION` impide el borrado, `CASCADE` borra también las dependientes, `SET NULL` y `SET DEFAULT` cambian la referencia (tema 8.3). `TRUNCATE TABLE`, que no está en SQLite, vacía una tabla sin registrar cada fila; es más rápido pero no dispara los disparadores por fila.

### RETURNING

PostgreSQL, SQLite desde la versión 3.35 y otros SMBD permiten agregar `RETURNING columnas` a cualquiera de las tres sentencias, para obtener las filas afectadas con sus valores nuevos sin una consulta adicional; SQL Server usa `OUTPUT`. Es útil para obtener una clave generada o para registrar qué cambió.

### Transacciones

Varias sentencias que deben aplicarse juntas, como el retiro de una cuenta y el depósito en otra, se agrupan en una **transacción**: `BEGIN`, las sentencias y `COMMIT` para confirmar, o `ROLLBACK` para deshacer todo. El SMBD garantiza las propiedades **ACID**: atomicidad, consistencia, aislamiento y durabilidad (tema 9). Dentro de una transacción, una verificación seguida de una modificación, como "si el saldo alcanza, retirar", debe hacerse de forma que otra transacción no cambie el saldo en medio. Lo más sencillo es poner la verificación en la propia sentencia, `UPDATE ... WHERE saldo >= monto`, y comprobar cuántas filas cambió.

```mermaid
flowchart TD
    B["BEGIN"] --> U1["UPDATE origen: saldo - monto si alcanza"]
    U1 --> C1{"¿Cambió una fila?"}
    C1 -->|no| RB["ROLLBACK"]
    C1 -->|sí| U2["UPDATE destino: saldo + monto"]
    U2 --> C2{"¿Cambió una fila?"}
    C2 -->|no| RB
    C2 -->|sí| CM["COMMIT"]
```

### Buenas prácticas

- Probar el `WHERE` con un `SELECT` antes de ejecutar un `UPDATE` o un `DELETE`, y hacerlo dentro de una transacción para poder deshacerlo.
- Declarar las reglas como restricciones (`CHECK`, claves foráneas), para que el SMBD rechace los cambios inválidos aunque la sentencia esté mal escrita.
- Mantener los datos derivados con disparadores, o calcularlos con vistas, en lugar de confiar en que cada aplicación los actualice.
- Para cambios masivos en tablas grandes, hacerlos por lotes, para no bloquear la tabla ni hacer crecer la bitácora de transacciones.

### Implementación en Python

FROM`, con `IN` y con `NOT EXISTS`. Para el ejercicio 3 reparte aumentos de salario dentro de un presupuesto, implementa una transferencia atómica que se revierte si falta saldo o la cuenta destino no existe, y aplica la inflación acumulada por categoría.

db.executescript("""
CREATE TABLE empleados (id INTEGER PRIMARY KEY, nombre TEXT, depto TEXT, salario NUMERIC, evaluacion INTEGER);
CREATE TABLE presupuesto (depto TEXT PRIMARY KEY, aumento_max NUMERIC);
INSERT INTO empleados VALUES (1, 'Ana', 'TI', 40000, 5), (2, 'Beto', 'TI', 30000, 3), (3, 'Carla', 'TI', 35000, 4),
                             (4, 'Dante', 'Ventas', 25000, 5), (5, 'Eva', 'Ventas', 28000, 2);
INSERT INTO presupuesto VALUES ('TI', 4000), ('Ventas', 3000);
""")
antes = dict(db.execute("SELECT depto, SUM(salario) FROM empleados GROUP BY depto"))
# aumento deseado por evaluación; si el departamento no alcanza, se escala proporcionalmente
db.execute("""
WITH deseado AS (SELECT id, depto, salario * CASE evaluacion WHEN 5 THEN 0.08 WHEN 4 THEN 0.05 WHEN 3 THEN 0.02 ELSE 0 END AS a
                 FROM empleados),
     factor AS (SELECT d.depto, MIN(1.0, p.aumento_max / SUM(d.a)) AS f FROM deseado d JOIN presupuesto p USING (depto) GROUP BY d.depto)
UPDATE empleados SET salario = ROUND(salario + (SELECT d.a * f.f FROM deseado d JOIN factor f USING (depto) WHERE d.id = empleados.id), 2)
""")
print("3.1:", db.execute("SELECT nombre, salario FROM empleados ORDER BY id").fetchall(),

                    INSERT INTO cuentas VALUES ('A', 1000), ('B', 200);""")
def transferir(origen, destino, monto):
    try:
        db.execute("BEGIN IMMEDIATE")                      # bloquea la base para escribir antes de leer el saldo
        if db.execute("UPDATE cuentas SET saldo = saldo - ? WHERE numero = ? AND saldo >= ?", (monto, origen, monto)).rowcount != 1:
            raise ValueError("saldo insuficiente o cuenta inexistente")
        if db.execute("UPDATE cuentas SET saldo = saldo + ? WHERE numero = ?", (monto, destino)).rowcount != 1:
            raise ValueError("cuenta destino inexistente")
        db.execute("COMMIT"); return "hecha"
    except (ValueError, sqlite3.Error) as e:
        db.execute("ROLLBACK"); return f"revertida ({e})"
for o, d, m in (("A", "B", 300), ("B", "A", 900), ("A", "Z", 100)):
    print(f"3.2 transferir {m} de {o} a {d}:", transferir(o, d, m), "| saldos", db.execute("SELECT * FROM cuentas ORDER BY numero").fetchall())

# --- Ejercicio 3.3: inflación acumulada por categoría ---
db.executescript("""CREATE TABLE inflacion (categoria TEXT, mes TEXT, tasa NUMERIC);
INSERT INTO inflacion VALUES ('Electrónicos', '2026-08', 0.004), ('Electrónicos', '2026-09', 0.006), ('Electrónicos', '2026-10', 0.005),
                             ('Hogar', '2026-08', 0.010), ('Hogar', '2026-09', 0.008), ('Hogar', '2026-10', 0.012);""")
# la inflación acumulada es el producto de (1 + tasa); el logaritmo convierte el producto en una suma agregable
db.execute("""UPDATE productos SET precio = ROUND(precio * (SELECT EXP(SUM(LN(1 + tasa))) FROM inflacion i
                                                          WHERE i.categoria = productos.categoria), 2)
              WHERE categoria IN (SELECT categoria FROM inflacion)""")
print("3.3 acumulada:", db.execute("SELECT categoria, ROUND(100 * (EXP(SUM(LN(1 + tasa))) - 1), 3) FROM inflacion GROUP BY categoria").fetchall(),
      "| suma simple:", db.execute("SELECT categoria, ROUND(100 * SUM(tasa), 3) FROM inflacion GROUP BY categoria").fetchall())
tabla("    precios", "nombre, precio")

### Ejercicios Propuestos

1. **Actualizaciones básicas.** Con `productos(id, nombre, precio, stock, categoria, fecha_actualizacion)`, aumenta 8 % el precio de los productos de la categoría "Electrónicos", reduce en 5 unidades el stock de los productos con precio mayor que 500 y pon la fecha de hoy en los productos modificados.

2. **Con subconsultas.** Con `ventas(id, producto_id, cantidad, fecha)`, resta del stock las cantidades vendidas el último mes, aumenta 10 % el precio de los productos con más de 100 unidades vendidas y marca como inactivos los productos sin ventas en los últimos 6 meses.

3. **Actualizaciones complejas.** Ajusta los salarios según la evaluación de desempeño y el presupuesto de cada departamento; escribe una transacción que transfiera fondos entre cuentas verificando el saldo, y actualiza los precios con la inflación acumulada de cada categoría.

### Soluciones

**Ejercicio 1.** `UPDATE productos SET precio = ROUND(precio * 1.08, 2) WHERE categoria = 'Electrónicos'`. Para el stock, la condición debe incluir `stock >= 5`: la cafetera tiene 3, y sin esa condición el `CHECK (stock >= 0)` rechaza la sentencia **completa**, como muestra el programa, y no cambia ninguna fila. Si en cambio se quiere dejar en 0 los que no alcanzan, se usa `SET stock = MAX(stock - 5, 0)`, o `GREATEST` en otros SMBD. Para la fecha hay dos opciones: incluirla en cada `UPDATE` (`SET ..., fecha_actualizacion = CURRENT_DATE`) o, mejor, un disparador `AFTER UPDATE OF precio, stock` que la ponga siempre, para que ninguna aplicación lo olvide. El disparador del programa compara los valores con `IS NOT`, para no marcar las filas cuyo valor no cambió.

**Ejercicio 2.** "El último mes" se interpreta como el mes calendario anterior, del 1 al 31 de octubre; "los últimos 30 días" sería otra consulta. La resta se hace con `UPDATE ... FROM` sobre una subconsulta agregada por producto, para que cada producto se reúna con una sola fila; el estándar lo escribe como `SET stock = stock - (SELECT COALESCE(SUM(cantidad), 0) FROM ventas WHERE ...)`, donde `COALESCE` evita que los productos sin ventas queden con stock nulo. El aumento usa `id IN (SELECT producto_id ... HAVING SUM(cantidad) > 100)`: solo los audífonos, con 115 unidades. Los inactivos se marcan con `NOT EXISTS` de una venta en los últimos 6 meses, desde el 3 de mayo: la cafetera y la licuadora. Con `NOT IN` habría que excluir los `producto_id` nulos (tema 6.3). Marcar es mejor que borrar, porque los productos inactivos siguen teniendo ventas históricas que hacen referencia a ellos.

**Ejercicio 3.**

1. **Salarios:** el aumento deseado depende de la evaluación, 8 % para un 5, 5 % para un 4 y 2 % para un 3. Si la suma de un departamento excede su presupuesto, todos se escalan por el mismo factor, $\min(1, \text{presupuesto} / \text{suma}).$ En TI, los aumentos deseados suman 5550 y el presupuesto es 4000, así que se aplica el 72 %; en Ventas suman 2000 y caben en 3000. Todo se hace en un solo `UPDATE` con expresiones `WITH`, así que los cálculos usan los salarios anteriores.
2. **Transferencia:** se abre la transacción con `BEGIN IMMEDIATE`, que en SQLite reserva la escritura desde el principio; se resta del origen solo si el saldo alcanza, se suma al destino, y se confirma únicamente si cada `UPDATE` cambió exactamente una fila. Si no, `ROLLBACK`. El `CHECK (saldo >= 0)` es una segunda defensa. En el programa, la segunda transferencia se revierte por saldo insuficiente y la tercera por una cuenta destino inexistente, en ambos casos sin cambiar ningún saldo.
3. **Inflación:** la inflación acumulada no es la suma de las tasas mensuales, sino $\prod_i (1 + r_i) - 1.$ SQL no tiene un agregado de producto, pero $\prod_i (1 + r_i) = \exp\big(\sum_i \ln(1 + r_i)\big),$ que sí se puede calcular. En el ejemplo, 1.507 % en lugar de 1.5 % para Electrónicos y 3.03 % en lugar de 3.0 % para Hogar; la diferencia crece con el número de periodos y con las tasas.
