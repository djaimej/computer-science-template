# Introducción a las Ciencias de la Computación - Hilos de ejecución y multi-proceso (threads)

## 9.5 Depuración en hilos de ejecución.

---

Depurar un programa secuencial es, en principio, un proceso reproducible: con los mismos datos, el error aparece siempre en el mismo lugar. Con hilos esto deja de ser cierto. El error puede depender de una intercalación que ocurre una vez en mil ejecuciones, solo en la máquina del cliente o solo bajo carga, y a menudo **desaparece al intentar observarlo**, porque agregar una impresión o un punto de ruptura cambia los tiempos. A estos errores se les llama, en broma, *heisenbugs*. Esta página presenta los tipos de errores concurrentes, las herramientas para observarlos y las estrategias para encontrarlos y, sobre todo, para prevenirlos.

### 1. Los errores típicos

| Error                    | Síntoma                                                        | Causa                                                    |
| ------------------------ | -------------------------------------------------------------- | -------------------------------------------------------- |
| condición de carrera     | resultados incorrectos e intermitentes, datos corruptos        | acceso no sincronizado a datos compartidos               |
| problema de visibilidad  | un hilo no ve los cambios de otro, ciclos que no terminan      | falta de `volatile` o de sincronización                  |
| bloqueo mutuo            | el programa se congela, sin consumir procesador                | ciclo de hilos que esperan candados ajenos               |
| inanición                | un hilo nunca avanza aunque el programa sí                     | otros hilos acaparan el candado o el procesador          |
| bloqueo activo (*livelock*) | los hilos trabajan sin parar pero no progresan              | hilos que se ceden el paso mutuamente una y otra vez     |
| hilo que no termina      | el programa no sale al terminar `main`                         | ejecutor sin cerrar, hilo no de servicio en ciclo        |
| excepción perdida        | una tarea deja de hacer su trabajo sin aviso                   | excepción en un hilo o en un `Future` que nadie consulta |

### 2. Observar el estado de los hilos: volcados de hilos

Un **volcado de hilos** (*thread dump*) es una fotografía de todos los hilos de la JVM: su nombre, su estado y su pila de llamadas, incluyendo qué candados tienen y cuál esperan. Es la herramienta principal cuando un programa se congela.

```bash
jps -l                       # lista los procesos Java y sus identificadores
jstack 12345                 # volcado de hilos del proceso 12345
jcmd 12345 Thread.print      # alternativa equivalente
```

En la terminal donde corre el programa también se obtiene con Ctrl+\ en Linux y macOS, o Ctrl+Break en Windows. Un fragmento típico:

```text
"transferencia-1" #21 prio=5 os_prio=0 tid=0x... nid=0x... waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
	at Banco.transferir(Banco.java:14)
	- waiting to lock <0x000000071a2b3c48> (a Cuenta)
	- locked <0x000000071a2b3c10> (a Cuenta)

Found one Java-level deadlock:
=============================
"transferencia-1":
  waiting to lock monitor 0x... (object 0x000000071a2b3c48, a Cuenta),
  which is held by "transferencia-2"
"transferencia-2":
  waiting to lock monitor 0x... (object 0x000000071a2b3c10, a Cuenta),
  which is held by "transferencia-1"
```

La JVM detecta los bloqueos mutuos entre candados y los informa al final del volcado. Tomar **varios volcados con unos segundos de diferencia** distingue un hilo congelado, que aparece siempre en la misma línea, de uno que solo está ocupado.

**Nombre a los hilos.** En un volcado, `"transferencia-1"` dice mucho más que `"Thread-7"`. Se asigna con el constructor de `Thread`, con `setName`, o con una fábrica de hilos para los ejecutores.

### 3. Detectar bloqueos mutuos desde el programa

La interfaz `ThreadMXBean` permite que el propio programa, o una herramienta de monitoreo, busque bloqueos mutuos:

```java
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;
import java.util.concurrent.CountDownLatch;

public class DetectarBloqueo {
    public static void main(String[] args) throws InterruptedException {
        Object a = new Object(), b = new Object();
        CountDownLatch ambosConUnCandado = new CountDownLatch(2);

        Thread t1 = new Thread(() -> tomarAmbos(a, b, ambosConUnCandado), "hilo-AB");
        Thread t2 = new Thread(() -> tomarAmbos(b, a, ambosConUnCandado), "hilo-BA");
        t1.setDaemon(true); t2.setDaemon(true);       // para que el programa pueda terminar
        t1.start(); t2.start();

        ThreadMXBean mx = ManagementFactory.getThreadMXBean();
        long[] ids = null;
        while (ids == null) {                           // espera a que se forme el bloqueo
            Thread.sleep(50);
            ids = mx.findDeadlockedThreads();
        }
        for (ThreadInfo info : mx.getThreadInfo(ids)) {
            System.out.println(info.getThreadName() + " espera un candado de " + info.getLockOwnerName());
        }
    }

    static void tomarAmbos(Object primero, Object segundo, CountDownLatch latch) {
        synchronized (primero) {
            latch.countDown();
            try { latch.await(); } catch (InterruptedException e) { return; }
            synchronized (segundo) {
                System.out.println("nunca se imprime");
            }
        }
    }
}
```

```text
hilo-AB espera un candado de hilo-BA
hilo-BA espera un candado de hilo-AB
```

El `CountDownLatch` fuerza la intercalación desfavorable: cada hilo toma su primer candado y espera a que el otro tome el suyo antes de pedir el segundo. Esta técnica de **forzar intercalaciones** es muy útil para convertir un error intermitente en uno reproducible.

### 4. Bitácoras

Las impresiones con `System.out.println` desde varios hilos se mezclan y no dicen quién las produjo. Un registro útil incluye al menos la hora con precisión de milisegundos y el **nombre del hilo**:

```java
static void log(String mensaje) {
    System.out.printf("%tT.%<tL [%s] %s%n", System.currentTimeMillis(),
                      Thread.currentThread().getName(), mensaje);
}
```

```text
10:42:07.311 [productor] puso 7
10:42:07.312 [consumidor-2] tomó 7
```

En programas reales se usa una biblioteca de bitácoras, como `java.util.logging`, Log4j o SLF4J, que agrega estos datos automáticamente. Hay que recordar que escribir en la bitácora cambia los tiempos y puede ocultar el error: un problema que desaparece al agregar mensajes es casi seguro una condición de carrera o de visibilidad.

### 5. Depuradores

Los depuradores de los entornos de desarrollo, como IntelliJ IDEA, Eclipse o VS Code, muestran la lista de hilos y la pila de cada uno. Al configurar un punto de ruptura se elige si debe suspender **solo el hilo** que lo alcanza o **todos** los hilos. Suspender solo uno permite avanzar los demás paso a paso y reproducir manualmente una intercalación específica, por ejemplo, detener al hilo A justo después de leer el contador y dejar que B haga su incremento.

### 6. Herramientas de análisis

- **VisualVM** y **Java Mission Control**, con *Java Flight Recorder*, muestran en el tiempo el estado de cada hilo, cuánto esperan en cada candado y qué los bloquea. Sirven para encontrar cuellos de botella por contención.
- **Analizadores estáticos**, como SpotBugs o las inspecciones de los entornos de desarrollo, señalan patrones sospechosos sin ejecutar el programa: campos accedidos con y sin sincronización, `wait` fuera de un ciclo, `notify` en lugar de `notifyAll`.
- **jcstress**, del proyecto OpenJDK, ejecuta millones de veces fragmentos concurrentes en distintas intercalaciones y reporta los resultados observados, incluidos los que el programador creía imposibles.

### 7. Estrategias

**Para reproducir:**

- **Pruebas de estrés:** ejecutar la operación sospechosa millones de veces, con más hilos que núcleos.
- **Forzar intercalaciones** con `CountDownLatch`, `CyclicBarrier` o pausas en puntos estratégicos.
- Probar en máquinas con distinto número de núcleos.

**Para diagnosticar:**

- Ante un congelamiento, tomar volcados de hilos antes que nada.
- Verificar invariantes con aserciones: si un invariante de una estructura compartida falla, la condición de carrera está en el código que la modifica.
- Revisar cada dato compartido y modificable y preguntarse qué candado lo protege; si no hay una respuesta única, ahí está el error.

**Para prevenir**, que es mucho más barato que depurar:

- Minimizar los datos compartidos y modificables: preferir objetos inmutables y confinamiento (subtema 9.3).
- Usar las abstracciones de alto nivel, como ejecutores, `BlockingQueue`, `ConcurrentHashMap` y variables atómicas, en lugar de `wait`, `notify` y candados manuales.
- Adquirir los candados siempre en el mismo orden global.
- Documentar qué clases son seguras para hilos y qué candado protege cada campo.

> **Conexión con CC.** Como las pruebas no pueden cubrir todas las intercalaciones, que crecen exponencialmente, los sistemas concurrentes críticos se analizan con **métodos formales**. La verificación de modelos, con herramientas como SPIN o TLA+, explora sistemáticamente todos los estados posibles de un algoritmo concurrente y encuentra bloqueos mutuos y violaciones de invariantes que ninguna prueba habría encontrado. Empresas como Amazon usan TLA+ para verificar el diseño de sus servicios distribuidos.

### Ejercicios propuestos

1. Ejecute `DetectarBloqueo` quitando las líneas `setDaemon`. Mientras está congelado, obtenga un volcado con `jstack` e identifique en él el bloqueo mutuo.
2. Corrija `DetectarBloqueo` aplicando un orden global a los candados y verifique que `findDeadlockedThreads` ya no encuentra nada.
3. Tome el programa `Carrera` del subtema 9.3 y escriba una prueba de estrés que lo ejecute 1000 veces y reporte cuántas veces el resultado fue incorrecto. Compare con 1, 2 y 8 hilos.
4. Use un `CountDownLatch` para forzar de manera reproducible la intercalación de la tabla del subtema 9.1, en la que se pierde un incremento.
5. Escriba un programa con un bloqueo activo: dos hilos que, al encontrar ocupado el candado del otro con `tryLock`, sueltan el suyo y vuelven a intentar inmediatamente. Observe el consumo de procesador y propóngale una solución.
6. Abra VisualVM o Java Mission Control, conéctelo al productor y consumidor del subtema 9.3 con varios productores y consumidores, e interprete la gráfica de estados de los hilos.
