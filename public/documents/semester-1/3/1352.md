# Introducción a las Ciencias de la Computación - Herencia

## 5.2 Aspectos principales de la herencia.

---

La herencia es poderosa pero exigente: una subclase queda ligada a su superclase y a todo lo que esta promete. Usarla bien requiere entender varios aspectos que van más allá de la sintaxis: qué significa realmente "es un", cómo se convierten las referencias entre tipos de la jerarquía, qué ofrece la clase raíz `Object`, cuándo es preferible la composición y qué condición debe cumplir toda subclase para no romper el programa: el principio de sustitución de Liskov.

### 1. "Es un" frente a "tiene un"

- **Herencia** expresa que la subclase **es un** caso particular de la superclase: un `Gerente` es un `Empleado`.
- **Composición** expresa que un objeto **tiene** a otro como parte o colaborador: un `Automovil` tiene un `Motor`.

```java
// Composición: Automovil delega en su motor, no lo extiende
class Motor {
    private boolean encendido;
    void encender() { encendido = true; }
    boolean estaEncendido() { return encendido; }
}

class Automovil {
    private final Motor motor = new Motor();
    void arrancar() { motor.encender(); }
}
```

**Prefiera la composición.** Muchas veces se usa herencia solo para reutilizar código, y eso genera problemas. Un ejemplo clásico de la propia biblioteca de Java es `Stack extends Vector`: como una pila "es un" vector, hereda métodos como `insertElementAt`, que permiten insertar en medio de la pila y romper su disciplina de "último en entrar, primero en salir". Una pila que **tiene** una lista y solo expone `push`, `pop` y `peek` no tiene ese problema.

### 2. Tipos estáticos, tipos dinámicos y conversiones

Como un `Gerente` es un `Empleado`, una variable de tipo `Empleado` puede referirse a un `Gerente`:

```java
Empleado e = new Gerente("Luis", 30000, 8000);   // conversión ascendente: siempre válida
```

- El **tipo estático** de `e`, el declarado, es `Empleado`. El compilador solo permite enviarle mensajes de `Empleado`: `e.setBono(5000)` no compila.
- El **tipo dinámico**, el del objeto real, es `Gerente`. Al ejecutar `e.salarioMensual()` se usa la versión de `Gerente`.

Para usar los métodos propios de la subclase hay que hacer una **conversión descendente** explícita, que se verifica al ejecutar:

```java
if (e instanceof Gerente g) {      // verifica y convierte en un solo paso (Java 16+)
    g.setBono(5000);
}
Empleado otro = new Empleado("Ana", 20000);
Gerente mal = (Gerente) otro;      // compila, pero lanza ClassCastException al ejecutar
```

Necesitar muchas conversiones descendentes suele indicar un diseño mejorable: si el código pregunta "¿de qué tipo eres?" para decidir qué hacer, probablemente ese comportamiento debería ser un método redefinido en cada subclase (subtema 5.3).

### 3. La clase `Object`

Toda clase hereda de `Object` estos métodos, entre otros:

| Método                | Comportamiento por omisión                  | Cuándo redefinirlo                                   |
| --------------------- | ------------------------------------------- | ---------------------------------------------------- |
| `toString()`          | nombre de la clase y un código hexadecimal  | casi siempre, para depurar y mostrar objetos         |
| `equals(Object o)`    | identidad, como `==`                        | cuando dos objetos con el mismo contenido deben ser iguales |
| `hashCode()`          | derivado de la identidad                    | **siempre** que se redefina `equals`                 |
| `getClass()`          | la clase del tipo dinámico                  | no se redefine                                       |

**Redefinir `equals` y `hashCode`.** El contrato exige que `equals` sea una relación de equivalencia, reflexiva, simétrica y transitiva (Estructuras Discretas, subtema 4.2), y que objetos iguales tengan el mismo `hashCode`. Si no se cumple, las colecciones como `HashSet` y `HashMap` dejan de funcionar correctamente.

```java
import java.util.Objects;

public final class Punto {
    private final int x, y;
    public Punto(int x, int y) { this.x = x; this.y = y; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Punto otro)) return false;
        return x == otro.x && y == otro.y;
    }

    @Override
    public int hashCode() { return Objects.hash(x, y); }

    @Override
    public String toString() { return "(" + x + ", " + y + ")"; }

    public static void main(String[] args) {
        java.util.Set<Punto> s = new java.util.HashSet<>();
        s.add(new Punto(1, 2));
        System.out.println(s.contains(new Punto(1, 2)));   // true gracias a equals y hashCode
    }
}
```

Para clases que solo agrupan datos inmutables, los **registros** de Java generan automáticamente constructor, métodos de acceso, `equals`, `hashCode` y `toString`: `record Punto(int x, int y) {}`.

### 4. Sobrescritura, sobrecarga y ocultamiento

| Concepto        | Qué es                                                         | Se decide        |
| --------------- | -------------------------------------------------------------- | ---------------- |
| Sobrescritura   | la subclase redefine un método heredado con **la misma firma** | al ejecutar, según el tipo dinámico |
| Sobrecarga      | varios métodos con el mismo nombre y **distintos parámetros**  | al compilar, según los tipos estáticos de los argumentos |
| Ocultamiento    | la subclase declara un método `static` o un atributo con el mismo nombre que uno de la superclase | al compilar |

Un error clásico es querer redefinir `equals` escribiendo `public boolean equals(Punto o)`: como el parámetro es `Punto` y no `Object`, eso es una **sobrecarga**, no una sobrescritura, y las colecciones seguirán usando el `equals` de `Object`. La anotación `@Override` detecta este error.

### 5. Controlar la herencia

- Un método `final` no puede redefinirse en las subclases.
- Una clase `final` no puede extenderse. Las clases inmutables, como `String`, suelen ser `final` para que ninguna subclase pueda volverlas mutables.
- Desde Java 17, una clase `sealed` puede enumerar exactamente qué subclases permite: `sealed class Figura permits Circulo, Rectangulo`.
- Los constructores no deben llamar métodos que las subclases puedan redefinir, porque se ejecutarían antes de que la subclase haya inicializado sus atributos.

### 6. El principio de sustitución de Liskov

Barbara Liskov formuló en 1987 la condición que debe cumplir toda subclase: **cualquier código que funciona correctamente con objetos de la superclase debe seguir funcionando si recibe objetos de la subclase**. No basta con que compile: la subclase debe respetar las promesas de la superclase.

**El ejemplo del rectángulo y el cuadrado.** Matemáticamente, un cuadrado es un rectángulo. Pero considere:

```java
class Rectangulo {
    protected int ancho, alto;
    void setAncho(int a) { ancho = a; }
    void setAlto(int h) { alto = h; }
    int area() { return ancho * alto; }
}

class Cuadrado extends Rectangulo {
    @Override void setAncho(int a) { ancho = a; alto = a; }   // mantiene los lados iguales
    @Override void setAlto(int h) { ancho = h; alto = h; }
}

public class Liskov {
    static void probar(Rectangulo r) {
        r.setAncho(5);
        r.setAlto(4);
        System.out.println(r.area());   // un Rectangulo promete que el área es 20
    }
    public static void main(String[] args) {
        probar(new Rectangulo());       // 20
        probar(new Cuadrado());         // 16: la promesa se rompe
    }
}
```

El método `probar` es correcto para rectángulos y falla con cuadrados, así que, **en este diseño con métodos de actualización**, `Cuadrado` no debe ser subclase de `Rectangulo`. Si ambas clases fueran inmutables, sin `setAncho` ni `setAlto`, la herencia sí sería válida. La lección: la relación "es un" se refiere al **comportamiento** de los objetos, no solo a su clasificación en el mundo real.

Otro síntoma de violación es una subclase que lanza `UnsupportedOperationException` en un método heredado, como un `Pinguino extends Ave` que no puede `volar()`. Si no toda ave vuela, `volar()` no debería estar en `Ave`.

> **Conexión con CC.** Las bibliotecas con jerarquías profundas sufren el problema de la **clase base frágil**: un cambio aparentemente inocente en una superclase rompe subclases escritas por otras personas. Por eso los diseños modernos tienden a jerarquías poco profundas, a composición y a interfaces, y lenguajes recientes como Go o Rust ni siquiera tienen herencia de implementación.

3. Redefina `equals`, `hashCode` y `toString` en la clase `Empleado`, considerando iguales a dos empleados con el mismo nombre. ¿Debe un `Gerente` ser igual a un `Empleado` con el mismo nombre? Discuta la simetría.
